9.2 Scalability

The sizing of A-09 is 200 offerings and 20,000 participants a year, with peaks of 2,000 registrations within a few hours. The design must allow ten times the volume without a change of architecture ({{nfr-growth}}).

Scalability measures

9.3 Availability

The targets are 99.5% availability during working hours, 08:00 to 18:00 Monday to Friday ({{nfr-avail}}), and 99.5% for the public verification page at all hours ({{nfr-verifyavail}}).

  • Single points of failure. In Release 1 the database and Redis are single instances. Failure of either stops the system until it is restored; the recovery time is that of {{nfr-recover}}. A standby database is a later option and is not needed to meet 99.5%.
  • Verification page. It reads one table and can be served by a second web node and a database read connection. It does not depend on Redis for a session, and the rate limiter falls back to allowing requests if Redis is down, so verifiers are not locked out by a cache failure.
  • External systems. A failed adapter never stops a function that does not use it. Dependent jobs wait and retry ({{nfr-adapterfail}}).
  • Maintenance. Planned maintenance is announced 48 hours ahead through the banner and kept outside working hours ({{nfr-maint}}). A deployment uses maintenance mode for the migration step only, and migrations are written to be backward compatible with the previous release where practicable (expand, then contract).
  • Errors. Users see a clear message with a reference code; the detail is logged ({{nfr-errors}}).

9.5 Accessibility

The interface conforms to WCAG 2.1 level AA ({{nfr-wcag}}, {{ir-accessible}}). The rules below are build rules for developers; they are applied once, in the shared components, and checked in tests.

  1. Every control works by keyboard. Dialogs and drawers trap focus, close on Escape and return focus to the control that opened them. Table rows that open records are focusable and respond to Enter and Space.
  2. Every field has a visible label tied to the input. Placeholders never stand in for labels. Errors are linked to the field with aria-describedby and announced in a live region.
  3. Status is never shown by colour alone: x-ui.status-tag always prints the word. The stage track gives each stage a text state.
  4. Text contrast is at least 4.5:1, including white and light-blue text on the navy side navigation. Tokens that fail the ratio are not added to tokens.css; a CI step checks the token pairs.
  5. Images have text alternatives. Icons are decorative unless they carry the only label, in which case they have an accessible name.
  6. The layout reflows to one column below 760 px; tables scroll inside their frame; the page does not scroll sideways ({{ir-responsive}}, {{nfr-mobile}}).
  7. Toasts use a polite live region. Idle timeout warnings use an alert dialog with a safe default.
  8. Pages for participants stay under 1.5 MB without media where practicable ({{nfr-lowbandwidth}}).
  9. Generated PDFs are tagged with the document language and have a logical reading order where Chromium supports it.

Checks: automated axe checks run in the Playwright suite on every main screen in both languages; a keyboard-only walk of the hand-off scenario is done by hand before each release.

9.6 Bilingual Operation

Every screen, notice and credential exists in Bahasa Melayu and English (AD-13, {{ir-lang}}). The language switch keeps the user on the same page with entered data ({{nfr-langswitch}}). Tests compare the two language files for missing keys and render each main screen in both languages. Bilingual content fields mark a missing language and a record cannot be issued as a credential in a language whose required fields are empty. Fonts are bundled so that long Malaysian names print in full ({{nfr-names}}).

9.8 Maintainability

  • Modularity. Modules and their allowed dependencies are enforced by Deptrac and architecture tests ({{nfr-modular}}).
  • Conventions. Laravel conventions, PSR-12, strict types and static analysis at level 8 ({{nfr-laravel}}).
  • Tests. Every business rule has at least one automated test, and the suite runs on every change ({{nfr-rulestests}}). Test names carry the requirement key, which gives a traceability list for free.
  • Portability. Queries use Eloquent and the query builder; vendor-specific features appear only in migrations and are listed in the release notes ({{nfr-dbportable}}).
  • Configuration. Environment values are configuration and business values are settings ({{nfr-config}}, {{fr-settings}}).
  • Documentation. The SDD, adapter interfaces, CSV templates and operating procedures are updated with each release ({{nfr-docs}}).
  • Administration without the database. Users, roles, settings, templates, reference data and adapter modes are managed in the interface ({{nfr-admin}}).

10. Deployment and Operations

This section describes where MCMS runs, how a change reaches production, and how it is watched. The hosting is Linux virtual machines at the UTeM data centre, which is an assumption awaiting confirmation (AD-18, A-09, {{nfr-deploy}}).

10.1 Environments

Environments and their settings

Development and test environments hold no real personal data unless it is masked ({{nfr-envs}}). Only the stub identity provider and the demo clock are limited to non-production, and the start-up check described in Section 3.6 enforces it (AD-06, AD-18).

10.2 Deployment Architecture

All traffic uses HTTPS (TLS 1.2 or later) ({{ir-https}}, {{sr-tls}}). The database, Redis and MinIO accept connections only from the web and worker VMs. Only the proxy is reachable from users. The database account used by the application has no UPDATE or DELETE right on the audit table (AD-11); migrations run under a separate account.

10.3 CI/CD Pipeline

Pipeline steps

The artefact is built once and promoted unchanged; only configuration differs between environments ({{nfr-config}}, {{nfr-deploy}}). The deployment procedure is a script in deploy/ and is documented in the operations guide so that it is repeatable. A rollback restores the previous artefact; a migration that cannot be reversed is announced as such in the release notes and a database backup is taken before it runs.

10.4 Configuration and Secrets

  • Environment values are held in .env files that are created on each server by the deployment, not committed to the repository.
  • Secrets (database password, Redis password, MinIO keys, Entra ID client secret, SMTP credentials) are held in the secret store of UTeM ICT or, until one is agreed, in a file readable only by the application account (assumption). Secrets are rotated when a person with access leaves.
  • The credential signing private key is never an environment value. It stays in the CODL key vault and the application asks the vault to sign (AD-09, {{sr-keys}}). Key rotation does not invalidate credentials already issued.
  • Logs and error pages never print secrets ({{nfr-applog}}).

10.5 Database Migrations and Seed Data

  • Migrations. Versioned migrations are the only way to change the schema ({{nfr-migrations}}). They run in the deployment under the migration account. A migration is small, backward compatible with the previous release where practicable, and tested on a copy of staging.
  • Reference seeder. ReferenceSeeder loads reference data that production needs: roles, status lists, default settings, notification templates, PTj and programme lists as agreed with the offices ({{fr-refdata}}, {{dr-refimport}}).
  • Sample world. SampleWorldSeeder loads the prototype's sample world: users in every role, three offerings of the three categories, one participant followed through every stage, and the stub adapter behaviour of PRD Section 7. It is the seed of the development, test and staging environments and the base of the Pest and Playwright tests. It is never run in production.
  • No legacy credentials. No credential is created for results before go-live ({{dr-nolegacycred}}).
  • Production data. Production starts with the reference seed and the first administrators. All other data comes from use.

10.6 Monitoring and Alerting

Monitored items and alert rules

Planned maintenance is announced 48 hours ahead in the banner ({{nfr-maint}}). An incident procedure covering detection, containment, notification and recovery is written before the first production release ({{sr-incident}}), and a security test is carried out first ({{sr-pentest}}).

10.7 Release Flags: Release 1 and Later

Release switches

Release 1 contains all four increments (1.1 to 1.4) of the PRD. A flag that is off hides its screens and routes, and the manual path remains in use. Turning a flag on in production follows the pipeline: change the configuration in staging, test, approve, then change production.
