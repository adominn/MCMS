7. Process Design

This section shows how the modules of Section 4 work together in the main business processes. Each process has a sequence diagram, a table of checks, confirmations, events and failure paths, and the requirements it satisfies. Behaviour follows the approved prototype acts and the SRS functional requirements. Event names are PastTense class names. The numbered event list (EV-xx) is owned by Section 4, and these names are used here without numbers so that the two sections stay consistent. Job names are class names for the same reason (JB-xx numbers are in Section 4).

Conventions that apply to every process:

  • Every action on a record is authorised by a Laravel Policy for role, scope and separation of duties (AD-07), before any change is made.
  • Every state change and its audit row are written in one database transaction (AD-11). Domain events are dispatched after commit.
  • A confirmation dialog is shown for every irreversible action ({{ir-confirm}}). The dialog names the effect. The server also checks that the confirmation token was posted.
  • Notifications are stored first and sent by a queued job (AD-15). A failed notification never rolls back the business change ({{fr-ihretry}}).
  • Dates and times are stored in UTC and shown as Malaysia time ({{ir-time}}). The demo clock is available only outside production (AD-18).

7.1 Propose, Review, Endorse and Record the Senate Decision

A lecturer prepares a proposal for a new micro-credential. The deputy dean of the PTj assigns reviewers, a colleague reviews after declaring any conflict of interest, and the deputy dean endorses. The Senate does not use MCMS, so the deputy dean records the Senate decision with its meeting reference (D-11).

7.2 Material Change to an Approved Version

An approved version is never edited. A change creates a new version as a copy. A minor change is logged and acknowledged. A material change repeats the review and approval path of process 7.1 and does not take effect until approved.

7.4 Register and Pay

A student registers while the window is open and capacity remains. A fee leads to Pending payment and a payment call through the payment adapter (a stub in Release 1). Capacity is checked under a row lock so that the last seat cannot be given twice. Payment calls carry an idempotency key.

The confirmation starts the issuing job, which runs the pre-issue checks, signs each credential, renders the PDF and sends the notifications. The deputy dean does not issue by hand (UI/UX spec §2.2).

7.7 Credential Correction, Replacement and Revocation

Credentials are never deleted. A confirmed error is corrected as a new revision, a replacement has a new ID and is linked to the old one, and a revocation is recorded with a stated reason. The deputy dean of the owning PTj records the decision. CODL has no part in these actions (D-12).

7.12 Job Designs

All background work runs as Laravel queued jobs on Redis under Horizon (AD-05, {{nfr-queue}}). The scheduler starts timed jobs ({{nfr-scheduler}}). Rules common to all jobs:

  • A job is idempotent. It records its natural key before it acts, and a second run with the same key returns the first result.
  • A job is retried with a growing delay (for example 1, 5, 15 and 60 minutes) up to a set number of tries. When tries are exhausted the job moves to the failed-job list, and an alert is sent to CODL ({{fr-ihretry}}).
  • A job never holds a database transaction while it calls an external service. It reads, calls, then writes in a short transaction.
  • A job writes progress to a job_runs row (total, done, failed, status). The screen polls that row.
  • A failure of one item does not stop the others. Failures are listed with a reason.
