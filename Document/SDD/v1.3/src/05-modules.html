4. Module Design

This section designs the seventeen modules of MCMS (AD-01). Each module has the same sub-structure: a fact sheet, a table of actions, and, where the module owns a record with a life cycle, a state machine. Section 4.19 collects the domain events (EV-xx) and the jobs (JB-xx) in two catalogues. Section 6 lists the events again and Section 7 shows the main flows as sequences.

4.1 Conventions for Module Descriptions

The following conventions apply to every module in this section.

  • Fact sheet. Purpose, the SRS requirements delivered, the tables owned (snake_case plural, columns defined in Section 5), the screens served by their UI/UX specification ID, the events published and consumed, and the jobs run.
  • Tables owned. Only the owning module reads or writes its tables. Other modules call its public service interface or react to its domain events (AD-01).
  • Actions. An action is one public service operation, called by a Livewire component or a controller. Every action runs under a Laravel Policy that checks role, scope and separation of duties on the record (AD-07). The policy column names the rule that is not obvious from the role alone.
  • Confirmation. "Yes" means the interface shows a confirmation dialog before the action runs ({{ir-confirm}}). An action with "Yes" is irreversible, submits, approves, issues, revokes or changes a setting. The server does not rely on the dialog: it checks the same rules again.
  • Roles. Student (P8), Lecturer (P1), Deputy dean of the PTj (P2), colleague reviewer (X1), industry expert (X2), public verifier (X3), CODL system administrator (S1) and CODL technical operator (P5). CODL roles never pass an academic policy (D-12). The Senate has no login: the deputy dean records each Senate decision with its meeting reference (D-11).
  • Audit. Every action that changes a record writes an audit_events row in the same database transaction (AD-11). The tables in this section do not repeat this.
  • No deletion. A correction creates a new revision linked to the old record. No module offers a delete action on a business record (D-20, {{dr-nodelete}}).
  • Events. A service publishes an event after its transaction commits (afterCommit). Listeners are queued on the default queue and are idempotent: each listener stores the event ID it has handled. Events carry record IDs and version numbers, not personal data. Event names are PastTense class names.
  • Jobs. Every job has a queue, an idempotency key and a retry rule (Section 4.19). A job that exhausts its retries writes an integration_jobs row in the failed state and raises AdapterCallFailed or a module-specific failure event.
  • State machines. Status words are those of UI/UX Specification v1.1 section 4.8. Each transition names the action that causes it. A state change is made only by the owning module's service.
  • Derived wording. Credit, MQF level and QV wording is read from verified records at the time of use and is never typed or stored as free text (D-17, {{dr-derived}}).

4.19 Event and Job Catalogues

4.19.1 Domain events

The event IDs below are final for this document. Section 6 and Section 7 reuse them. Cross-module reactions that matter most are:

  • EV-29 ResultsVerified lets MD-09 issue a Digital Badge for a verified module. It does not complete the micro-credential.
  • EV-31 CompletionConfirmed starts JB-01 in MD-09, which runs the pre-issuance checks and issues the certificate and Digital Credential. No other event issues these (D-29).
  • EV-32 CredentialIssued lets MD-11 prepare an ACR for an eligible UMC or a QV-valid SAMC. It never prepares one for an MCE.
  • EV-45 ConsentGiven puts a confirmed ACR in the deposit queue. Without it no deposit can be recorded.
  • EV-47 DepositRecorded sets the ledger credit to Available and the expiry to the deposit date plus the credit validity setting (10 years).
  • EV-52 TransferDecided with an approved outcome sets the credit to Provisionally redeemed, so a second application cannot use it.
  • EV-42 QvLapsed stops QV wording on new credentials and stops new ACR eligibility for the SAMC. Earlier credentials keep their status valid at the issue date.

4.19.2 Jobs

Queues are named in AD-05: default, notifications, imports, credentials, reports, integration and default. Scheduled jobs are started by the Laravel scheduler and dispatch to a queue. Long jobs report progress in job_runs. Alert jobs record each sent alert in alert_log so a re-run sends nothing twice. The idempotency key is stored on the job record, and a second run with the same key does nothing. Retry delays grow at each attempt (backoff).
