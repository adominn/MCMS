6. Interface Design

This section describes how MCMS meets its users and how it exchanges data with other systems. Screen-level layouts are in the UI/UX Specification v1.1 and are not repeated. The external interfaces implement SRS Section 5 ({{ir-adapter}}, {{ir-stubs}}, {{ir-mode}}): each is a PHP interface with Stub, Manual and Live implementations chosen by configuration (AD-08), and every call is recorded in integration_calls (Section 5).

6.1 User Interface

6.1.1 Route Conventions

MCMS has one web application with three front ends that share one design: the public pages, the participant portal and the staff portal ({{ir-responsive}}). The prototype uses hash routes such as #/dd/verify/DS-2026-2. In MCMS the same path is a real URL: /dd/verify/{cohort}.

Route conventions

6.1.2 Page Anatomy

Every signed-in page is rendered by the shell component and has the same parts ({{ir-home}}, UI/UX Specification Section 4):

  • Top bar with the search box, the language switch, the notification bell with the unread count and the profile menu.
  • Side navigation in navy, built from the role's menu. Counts on menu items come from the same query as the task queue.
  • Page head with the title, a short subtitle and the primary action. Records show a stage track for the recognition stage they belong to ({{ir-stagecolours}}).
  • "Needs you" panel on list pages, listing the items the user must act on first.
  • Panels and tables holding the content. A table is the DataTable Livewire component with search, sort, filters and pagination (5, 10, 25 or 50 rows).
  • Dialogs, drawers and toasts for every state change, as UI/UX Specification Sections 4.1 to 4.3 define. A state-changing button opens a confirmation dialog first ({{ir-confirm}}). The dialog calls a Livewire action. The action calls the application service of the owning module, inside a database transaction that also writes the audit row (AD-11).
  • Long jobs (credential issue, imports, large reports) show a JobProgress component that polls the matching job_runs row every two seconds and shows "issuing 14 of 27" ({{nfr-queue}}).

The shared Blade and Livewire components are listed in Section 3. Pages are full-page Livewire components, one per screen. A page that is only a view with no interaction may be a Blade view served by a controller.

The 114 screens of the approved prototype are listed in UI/UX Specification Section 6.6. {{tab:ifc-screens}} summarises them by role and names the owning modules. Screen IDs are used in tests and in Section 4.

6.2 External Interfaces

{{tab:ifc-summary}} lists the external interfaces. All of them run through the integration hub (MD-16). Outbound calls are placed on the integration queue and retried with increasing delay ({{fr-ihretry}}). A call that still fails is listed on the adapter status screen (CODL-08) and does not block the business process that created it. Retry follows JB-16 (RetryAdapterCallJob): back-off of 1, 5, 15 and 60 minutes, then Failed and EV-63. These values are configuration.

External interfaces, adapters and modes in Release 1

The student information system and Release 2 and 3 live connectors (UCreds, ABC, QVC and MQA, payment) have no Release 1 implementation. Each interface above already has the Stub and Manual classes, so a Live class is added without changing a business module ({{fr-lplive}}).

6.2.1 Microsoft Entra ID (OpenID Connect)

Sign-in uses Laravel Socialite with the Microsoft provider, set to the UTeM tenant (AD-06, {{ir-oidc}}). The flow is the authorisation code flow with PKCE. MCMS stores no password ({{fr-nosignup}}).

  1. The user opens /signin and chooses to sign in. MCMS redirects to the Entra authorisation endpoint with scopes openid profile email, a random state, a nonce and the PKCE challenge.
  2. Entra authenticates the user, applies Conditional Access (MFA for staff) and redirects to /auth/callback with a code.
  3. MCMS exchanges the code for tokens, checks the ID token (signature against the tenant keys, iss, aud, exp, nonce), and reads the claims in {{tab:ifc-oidc}}.
  4. MCMS finds the user by oid ({{fr-idmerge}}). If none exists it applies the first-sign-in rules ({{fr-firstlogin}}); an account that is not known and not pre-registered gets the "Account not recognised" page (CMN-04).
  5. A session is started. Idle timeout is 30 minutes, from the setting auth.idle_timeout_minutes, with a warning two minutes before ({{fr-session}}).

ID token claims used

The staff or matric number (users.institution_id) is read from a directory attribute delivered in the token. The attribute name is a configuration value that CODL confirms (DA to be added, see the report to the lead).

Sign-in error handling

6.2.2 UCreds: CSV Export of Enrolments

CODL exports the enrolments of an offering to a CSV file and loads it into UCreds by hand (CODL-07, {{fr-lpexport}}). A lecturer may also download the file from the cohort screen (LEC-10). Only participants whose enrolment status is Enrolled are included. The job (JB-03, ExportUcredsEnrolmentJob) runs on the imports queue, writes an export_files row, and stores the file in object storage ({{fr-lplog}}).

Enrolment export, template enrol v3 (file name enrol-{offering}.csv)

The file is UTF-8 (with no byte-order mark), comma-separated, with a header row, quoted fields where needed and line ends of CRLF ({{ir-csvtemplates}}). It carries no identity card number, email address or marks. The same export of the same offering and template version produces the same bytes in the same order (sorted by learner_id), so a repeated export does not create a conflicting file ({{ir-idempotent}}). The template version is stored on the import_files row and printed on the export document (DOC-15).

6.2.3 UCreds: CSV Import of Results

UCreds results are loaded from a CSV file (CODL-07, {{fr-lpimport}}). Imported results are stored as Provisional and create no achievement, badge or credential until the deputy dean verifies them ({{fr-lpstaged}}, {{br-verifyfirst}}). CODL cannot verify.

Results import, template results v3 (file name results-{offering}.csv)

Badge import, template badges v3 (file name badges-{offering}.csv)

A badge row is matched to the verified module achievement of that learner and stored in digital_badges (EV-27 BadgeImported). A badge without a verified achievement is flagged on the import report and not accepted ({{fr-lpbadge}}).

6.2.5 Email (SMTP)

The MailTransport interface is implemented with Laravel Mail over the UTeM SMTP relay, with TLS ({{ir-smtp}}, AD-15). Mail is sent from a monitored UTeM address set in configuration.

  • Outbox. A notification is first inserted into notifications (the user sees it in the bell at once). JB-05 (SendNotificationJob) on the notifications queue then sends the email. The send is idempotent per notification: a notification with email_status Sent is never sent again.
  • Content. The subject and body come from the published template version in the recipient's language ({{fr-ntlang}}). A message names the record and links to the page. It carries no marks, identity number or credential payload.
  • Mandatory notices (decisions on the user's records, credential actions, consent requests, enrolment changes) are always sent. Other notices follow preferences, and lecturers and deputy deans may choose a daily digest ({{fr-ntprefs}}, {{fr-ntdigest}}).
  • Failure. A transient SMTP error (for example 4xx) sets the call to retry with increasing delay. A permanent error (5xx) or a bounce marks the notification Failed and lists it for the system administrator. The notification stays visible in the bell. Failures do not roll back the business action ({{nfr-adapterfail}}).
  • Test mailbox. Outside production the transport writes mail to the test mailbox (CODL-09), not to the relay.

6.2.6 ABC Deposit Export

The deputy dean prepares a batch of ACR that have consent and have been confirmed ({{fr-dpqueue}}). The export is a CSV file and a PDF document (DOC-10), for staff to send to ABC by an approved channel ({{ir-files}}). The format is not yet agreed with ABC (OI-11); the columns below follow the ACR fields of Appendix F3 and are the proposed format ({{fr-dpexport}}). JB-13 (ExportAbcDepositJob) builds the file. The batch can be exported again; the file for a given batch and format version has the same content.

ABC deposit export, proposed format abc v1 (file name {batch}.csv)

The prototype export has seven columns (reference, learner ID, micro-credential, credits, MQF level, completion date and consent date). The extra columns above come from {{fr-acrprep}} and are to be reduced or renamed when OI-11 is closed. The format version is stored in abc_batches.format_version.

  • Direction in. ABC returns the ABC reference by a channel outside MCMS. The deputy dean records, for each ACR, the deposit date, the ABC reference, the credits and the outcome (Successful, In process, Correction needed) ({{fr-dprecord}}). A reference range for a batch (for example 4391 to 4419) is entered once and expanded by the application.
  • Idempotency. One ACR has at most one deposit row (unique acr_id). Recording the same ACR again is refused and shows the earlier record ({{ir-idempotent}}).
  • Errors. An ACR whose consent is missing, declined or withdrawn is excluded, and the screen says which. A batch that is empty cannot be exported.
  • Later status. For every credit status change that must also be made in ABC, the user records whether it was done, with date and reference ({{fr-rdabcsync}}).

6.2.7 QVC and MQA Submission Package

For a SAMC, staff generate the submission package from the QV record (DD-14, LEC-16, {{fr-qvpackage}}). JB-14 (BuildQvPackageJob) on the reports queue builds a zip file, stores it in object storage and links it to the QV record (design: qv_submissions.package_file_id; Release 1 prototype: a package page with an evidence index, and the submission recorded on qv_records, Section 12). The package is for staff to submit to QVC and MQA by an approved channel. Staff then record the submission date, the QVC or MQA reference and the person who submitted in qv_submissions ({{fr-qvsubmit}}). The decision is recorded by hand ({{fr-qvresult}}).

Contents of the QV submission package

The package is generated again on request and each generation is stored as a new file; the one recorded as submitted is kept. A package cannot be generated while required checklist items are not accepted ({{fr-qvreadiness}}). A file that fails the malware scan is excluded and listed on the screen. The package is generated by a job, so a long build does not hold a web request ({{nfr-queue}}).

6.2.8 Public Verification Page and JSON API

Anyone can check a credential without signing in ({{fr-vfpage}}). The page is reached by the code, a link or a QR code that opens the link ({{ir-qrscan}}). The same data is served as JSON for other systems ({{ir-api}}). Responses follow {{nfr-verify}}: 95 percent within one second.

Verification endpoints

Rules for the response:

  • Fields. Only the holder's name, the credential name, the issuer, the issue date and the status (valid, corrected, replaced, revoked), plus any field listed in the setting verification.public_fields ({{fr-vffields}}). No identity card or passport number, matric number, email address or result is ever returned.
  • Lookup. The code is normalised (Section 5.5) and looked up by the unique public_code. A revoked credential still answers with status revoked. A credential that was corrected or replaced answers with that status and no link to the new credential.
  • Not found. An unknown or malformed code returns HTTP 404 with the same neutral body in every case: no hint whether a similar code exists ({{fr-vfnotfound}}). The code in the URL is never echoed in the body.
  • Rate limit. Verification and catalogue routes are limited by network address with Laravel's rate limiter ({{sr-ratelimit}}). A stricter limit applies to not-found answers, which are the signature of code guessing. Above the limit the response is HTTP 429 with a Retry-After header. The limits are configuration values (a DA is proposed in the report).
  • Logging. Each request writes a verification_logs row with the time, the credential (when found), the outcome and the network address. A not-found request stores a hash of the code, not the code ({{fr-vflog}}).
  • Headers. Cache-Control: no-store so a revocation is visible at once. The page has no cookies and no scripts from other sites.
  • File check. A verifier may upload a Digital Credential file. The page checks its signature against the published key and compares it with the stored payload hash ({{fr-vfsignature}}). The file is not stored.

6.2.9 Open Badges 3.0 Credential

A certificate is issued with a Digital Credential: a JSON-LD document that follows the Open Badges 3.0 and W3C Verifiable Credentials data models and is signed with Ed25519 using a Data Integrity proof of cryptosuite eddsa-rdfc-2022 (AD-09, {{fr-crformat}}). The document is built on the credentials queue by JB-22 (IssueCredentialJob, started by JB-01 after EV-31 CompletionConfirmed), signed by the SigningKeyStore, and stored in credentials.signed_payload. A module badge is a separate object in digital_badges and is imported from UCreds or issued by MCMS (EV-29, EV-33). The application never holds the private key: it sends the canonical hash to the key store and receives the signature ({{sr-keys}}). Blockchain is not used. The example is shortened; the host name is a placeholder.

  ],

  "issuer": {

    "type": ["Profile"],
    "name": "Universiti Teknikal Malaysia Melaka"
  },
  "validFrom": "2026-03-03T02:00:00Z",
  "name": "Data Structures",
  "credentialSubject": {
    "type": ["AchievementSubject"],
    "identifier": [{
      "type": "IdentityObject",
      "identityType": "name",
      "hashed": false,
      "identityHash": "Amir Hakimi"
    }],
    "achievement": {

  },
  "proof": {
    "type": "DataIntegrityProof",

  • Content. The credential carries the verified credit only when it is verified and valid. A SAMC adds the QV claim (QV status, MQF level) with the QV record reference ({{dr-derived}}). Names and descriptions are given in both languages by language maps in the stored version.
  • Identity. The document contains the holder's name as in the official record. It contains no identity card number, matric number or email address.
  • Key id. The verificationMethod names the key. A new key can be used for later credentials, and old keys stay published so earlier credentials still verify ({{sr-keys}}).
  • Download. The holder downloads the signed JSON and a PDF rendering (DOC-04) ({{fr-crwallet}}).

6.2.10 Printable Documents

Every printable document is a Blade A4 template with a print bar, rendered to PDF by headless Chromium (Spatie Browsershot) by JB-04 (RenderPdfJob) on the reports queue, except the certificate and Digital Credential, which are issued by JB-01 and JB-22 on the credentials queue (AD-10, {{ir-print}}). Templates are bilingual and versioned in templates and template_versions ({{fr-templates}}). The template version used is stored with the generated file. Certificates and Digital Credentials are rendered again from the stored signed payload, never from live data, so a reprint always matches what was issued.

Documents, template keys and outputs

Each page has a header with the UTeM name, the document title, the reference and the date, and a footer with the reference, the page number, the generation time and "Generated by MCMS". Participant documents are bilingual, with BM beneath EN. Documents that leave UTeM show no identity number, email or marks. A PDF is generated by a job and the user is notified when it is ready; small documents are returned directly.

6.3 Internal Event Catalogue

Modules communicate by domain events as well as by service interfaces (AD-01). An event is a PHP class named in the past tense. It is dispatched after the database transaction that caused it commits (afterCommit), and its listeners that do slow work run on a queue. The numbering EV-01 to EV-63 is owned by Section 4 and is reused here without change; {{tab:ifc-events}} repeats the catalogue of Section 4.19.1 so that Section 6 can be read alone. Jobs (JB-01 to JB-22) are listed in Section 4.19.2 and are named in the interface descriptions above.

Domain event catalogue (EV numbers from Section 4)

Rules for events: an event holds record identifiers and a few facts, not whole records. A listener must be safe to run twice (the same event delivered again does nothing new). A listener never changes a table of another module; it calls that module's service. Timed alerts (QV expiry at 180, 90 and 30 days, credit expiry at 365 and 90 days, an overdue decision after 14 days) are not events. They come from the scheduler and are made idempotent by alert_log (Section 5).
