2. Architecture Overview

This section shows how MCMS is divided: what surrounds it, what runs where, how the code is cut into modules, how modules talk to each other and to external systems, and how one request travels through the layers. It applies decisions AD-01 to AD-18 of Section 1. Module internals are in Section 4, data in Section 5, interfaces in Section 6.

2.1 System Context

MCMS is a new standalone system (SRS Section 2.1). People reach it through a browser. Every external system is reached through an adapter (AD-08, {{ir-adapter}}). {{fig:arch-context}} shows the systems MCMS exchanges data with in Release 1 and how each one is handled.

External systems and their Release 1 handling

Note: The student information system is not connected in Release 1 (SRS Section 2.1). The adapter pattern of Section 2.7 leaves room for it.

2.2 Runtime Containers

MCMS is one code base deployed as several processes (AD-05, AD-18). The web process and the queue workers run the same release of the application. No process keeps session state on its local disk ({{nfr-stateless}}): sessions and cache live in Redis.

2.3 Module Map

The code is split into the modules of {{tab:arch-modules}} (AD-01, {{nfr-modular}}). The SRS modules M1 to M16 are regrouped as the brief allows: M2 and M3 form one Curriculum module and M13 is split into Transfer and Pathways. MD-00 Platform is the shared kernel. It holds no business rule of its own.

Module map and dependencies

Two modules are called by every other module and so are not drawn as arrows: MD-15 offers the AuditRecorder contract and MD-16 offers the Notifier contract. Both depend only on MD-00 and receive other modules' facts through arguments or events, so they never depend back on a business module. {{fig:arch-deps-a}} and {{fig:arch-deps-b}} show the remaining dependencies in two parts; an arrow reads "uses the public contract of".

The dependency graph has no cycle. A build check (Section 3, deptrac) fails if a module uses a class outside the contracts of the modules it may depend on.

2.5 Communication Between Modules

Modules talk in two ways only (AD-01, {{nfr-modular}}).

  1. Public service contract. A module that needs an answer from another module calls an interface in that module's Contracts folder, for example AchievementRecordService::isComplete(). The interface returns DTOs or scalars, never Eloquent models.
  2. Domain event. A module that needs to tell others what happened raises an event. Listeners in other modules react. Events are named in the past tense and listed in Sections 4 and 6.

Rules of inter-module communication

Note: Credential issuing after completion is the one place where an event starts automatic work. CompletionConfirmed (EV-31) starts the issue job because the deputy dean's confirmation is itself the decision ({{br-verifyfirst}}). Nothing else is issued without a human decision.

2.6 Transactions and Events

Each action runs in one database transaction so that a multi-record change succeeds or fails as a whole ({{nfr-transactions}}). Inside the transaction an action locks the row it changes, checks the rule, saves, and writes the audit row. After the commit the events fire and jobs are queued. A job is idempotent: it can run twice without a second result, using the record's identifier as the idempotency key ({{ir-idempotent}}). Registration takes a row lock on the offering to keep capacity exact under concurrent submissions ({{nfr-capacity}}).

2.7 Adapter Pattern

Each external system has a PHP interface in MD-16 and three implementations (AD-08, {{ir-adapter}}, {{ir-stubs}}). The configuration for the environment chooses which one is bound in the service container, so a business module never knows which one it is using ({{ir-mode}}, {{nfr-config}}).
