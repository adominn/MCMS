Executive Summary

This audit delivers an exhaustive functional and technical evaluation of the UTeM Micro-Credential Management System (MCMS / ACESS). Built to support UTeM's lifelong learning and Malaysian Qualifications Framework (MQF) credit-bearing initiatives, MCMS implements the approved clickable prototype (D-38) across a modular Laravel 13 architecture connected to a PostgreSQL database schema.

Audit Objectives & Scope

The audit was executed under rigorous directives to identify all registered pages, evaluate actual versus intended behavior, trace database operations, verify role-based permissions, map end-to-end user flows, and identify disconnected or unfinished workflows. The scope encompasses:

  • All Seven (7) User Roles / Actors: Public / Guest, Student, Lecturer, Reviewer & Industry Expert, Deputy Dean, CODL Administrator, and Shared Authenticated Shell.
  • Complete Route Inventory: 221 registered routes (116 GET/HEAD endpoints and 105 POST/PUT state-transition actions).
  • Presentation Layer: 126 Blade templates across 24 module view directories.
  • Data Layer: 91 relational database tables across 20 schema migrations.
  • Execution & Integration: 36 module controllers, background event listeners, and external adapters.

Key Audit Findings

The system exhibits strong architectural discipline, with an append-only cryptographic audit chain (MD-15), strict separation of academic and administrative duties (D-28), and a fully functioning four-act demonstration scenario (FL-19) verifying core curriculum, learning, credit banking, and quality verification lifecycles. However, several critical gaps must be addressed before production pilot readiness:

  1. File Storage & Scanning Stand-Ins: Multiple production workflows (Quality Verification evidence, offering readiness evidence, UCreds CSV uploads) store textual file references rather than binary files in an object store with automated virus scanning.
  2. Server-Side PDF Generation: Official legal credentials (A4 certificate, student receipt, Academic Credit Record, Senate decision pack, transfer letter) rely on client-side browser print rendering rather than deterministic server-side PDF compilation.
  3. Bilingual UI Localization: While header toggles and Malay headings exist (lang/ms.json), subheadings, table headers, buttons, and validation messages remain predominantly in English.
  4. Asynchronous Processing Dependencies: File imports and 500-credential issuing batches run synchronously within HTTP requests, awaiting Redis/Horizon queue worker infrastructure.

The architecture establishes a clear separation between academic evaluation, quality assurance, system governance, and public verification.

1.2 Role Hierarchy & Separation of Duties (BR-01, BR-02)

To preserve academic integrity and prevent conflicts of interest, the system strictly enforces the following separation of duties:

  • Self-Review & Self-Approval Prohibition (FR-14, FR-71): A lecturer who authors a proposal cannot be assigned as its reviewer, cannot endorse the proposal, and cannot confirm its Senate approval.
  • Separation of Mark Entry and Verification (FR-120): A lecturer enters and submits raw marks; only the faculty Deputy Dean can verify marks and finalize achievements.
  • Two-Party Cohort Readiness (FR-86): A cohort readiness checklist must be completed by the lecturer and independently confirmed by the Deputy Dean before enrolment can open.
  • Administrative vs Academic Boundary (D-28): CODL Administrators hold zero authority over academic decisions (proposal approvals, grade adjustments, credit transfers, or completion confirmations). Their authority is strictly confined to technical settings, user accounts, and data interchange.

1.3 Page Types & Layout Architecture

In accordance with Decision D-38 and the approved clickable prototype (UIUX/v2/prototype), all pages adhere to a Summary-First information hierarchy utilizing the UTeM Carbon Design System with a Navy (#1e2a6e) sidebar navigation. Pages are categorized into six functional archetypes:

  1. Dashboard & Task Workspaces: Action-oriented hubs (e.g., Student Home, Task Queue, Approvals Hub) that display overdue action items, status counters, and active workflow links.
  2. Listing & Management Directories: Tabulated records featuring client-side search, type-aware column sorting, and pagination (suppressed for datasets of 10 or fewer rows).
  3. Multi-Step Guided Wizards: Stepped forms (e.g., 4-step Course Registration, Guided Category Wizard) with client/server validation, state retention, and explicit step indicators.
  4. Comprehensive Workspaces: High-density tabbed environments (e.g., 8-tab Curriculum Proposal Workspace, CQI Workspace) featuring live validation warnings, draft autosave, and status badges.
  5. Verification & Audit Portals: Cryptographic and data verification tools (e.g., Public Verification, Hash Chain Verification, Discrepancy Log) enforcing data integrity.
  6. Print & Export Layouts: Official institutional sheets (e.g., Certificate, Receipt, Academic Credit Record, Senate Decision Pack) formatted for standardized A4 presentation.

Several pages exhibit functional overlap and require architectural decisions regarding whether to retain, merge, or redesign them:

1. Internal Achievement Record (/my-record) vs Admin Record (/records/{enrolment})

  • Current Situation: /my-credit displays the balance of banked credits in ABC, while /my-credit/{id} displays the detailed Academic Credit Record and legal consent submission form.
  • Assessment: RETAIN AND ENHANCE. In accordance with D-38's Summary-First rule, the ledger provides the high-level credit balance overview, while the detailed legal text, MQA accreditation metadata, and consent buttons are properly isolated on the detail screen.

3. Printable Proposal View (/proposals/{id}/print) vs Senate Pack (/approvals/{id}/pack)

  • Current Situation: Both pages display an aggregated, non-tabbed representation of a micro-credential proposal.
  • Assessment: MERGE INTO STANDARDIZED TEMPLATE. The Printable Proposal view was developed for the authoring lecturer, while the Senate Pack was designed for the Deputy Dean. Both should share a single unified printable Blade component (layouts.print) with a conditional banner for Senate meeting metadata.

10.3 Missing Pages & Technical Gaps

  1. Official Senate Credit Transfer Decision Letter (DOC-12):
    Issue: When a Deputy Dean approves or rejects a credit transfer application, the decision is stored in transfer_decisions and viewable in the web table.     Issue: While the top navigation and static page <h1> headers are translated via lang/ms.json, table column headers, form input labels, validation alert messages, and button text remain in English.

11.3 Critical Vulnerabilities & Architectural Issues

Critical Finding 1: Unprotected Asynchronous Processing in Grade Staging
Severity: High • Affected Route: POST /admin/ucreds/imports/{id}/stage • Module: MD-06
Staging imported grades from UCreds runs synchronously within the PHP-FPM web request. For cohorts exceeding 300 learners, database transaction duration risks exceeding the default 60-second execution timeout, potentially resulting in partial grade staging.
Remediation: Implement Redis queue worker dispatch (StageGradesJob) with atomic transaction rollback.
Critical Finding 2: Lack of Cryptographic Hashing on Stored Evidence Files
Severity: High • Affected Route: POST /quality/{mc}/evidence • Module: MD-10
SAMC Quality Verification evidence items currently accept textual URLs or file reference strings without computing or recording a SHA-256 binary hash. An altered external document would not invalidate the evidence chain.
Remediation: Connect file inputs to an S3-compatible object store that calculates and immutably logs the binary SHA-256 hash in qv_evidence.file_hash.
Critical Finding 3: Missing Official Senate Transfer Decision Letter (DOC-12)
Severity: Medium • Affected Route: GET /transfers/{id} • Module: MD-12
When a credit transfer is approved, the decision updates the credit ledger, but no official printable Decision Letter (DOC-12) is generated for the student or Pejabat Pendaftar.
Remediation: Implement transfer.letter Blade view adhering to layouts.print.
