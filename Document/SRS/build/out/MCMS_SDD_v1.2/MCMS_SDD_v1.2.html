1. Introduction

1.1 Purpose

This Software Design Description (SDD) describes how the UTeM Micro-Credential Management System (MCMS) is built: its architecture, technology, modules, data, interfaces, processes, security, quality attributes and deployment. It is the last document of the set before the Release 1 build. Developers and AI development agents use it, together with the SRS and the UI/UX Design Specification, to build Release 1 without having to guess.

The SRS states what the system shall do, the PRD what to build first and why, and the UI/UX Design Specification how it looks and behaves. This SDD states how it is made. Where this SDD and the SRS differ on a requirement, the SRS prevails. Where this SDD and the UI/UX Design Specification differ on a screen's look or behaviour, the UI/UX Design Specification prevails. Where they differ on a term or decision, the Glossary and Decision Log prevails.

1.2 Scope

The design covers the complete Release 1 system: every requirement of the SRS marked SHALL (Section 11.2 gives the module for each area and the cross-cutting table gives the rest), every Release 1 feature of the PRD, and every screen and document of the approved UI/UX Design Specification v1.2. It shows where Release 2 and 3 capabilities (SHOULD and MAY) will attach, without designing them in detail, so that they can be added without rework (D-24).

In this SDD "the prototype" means the Release 1 prototype, the application designed here. The clickable HTML prototype of the UI/UX Design Specification is called the design prototype (D-31).

MCMS is a new standalone web application with its own database, which reaches other systems only through adapters (D-06). Learning content stays on UCreds. The national ABC platform and the QVC/MQA procedures are outside the system; MCMS prepares and records, and UTeM staff submit (D-14).

1.7 Design Principles

The design applies the principles of the UI/UX Design Specification (Section 2.1) to the code:

  • One stage, one record. Each recognition stage is its own table, its own action and its own event (D-15). No action changes two stages. Verifying results and confirming completion are separate actions; the system issues credentials only from a completion confirmation (D-29).
  • Authority in the policy layer. Who may decide is enforced in policies on the server for every request, not only by hiding buttons (D-11, D-12).
  • Generated recognition text. Credit, MQF level and QV wording is computed from verified records and templates, never stored as free text (D-17).
  • Nothing is erased. Corrections add revisions and events; the audit trail is append-only (D-20).
  • Rules are settings. Thresholds and approving roles are versioned settings, and decisions record the version in force (D-16).
  • Adapters at the edge. Every external system can run as a stub, manual exchange or live connection without changing the modules (D-06, D-14).

2.5 Communication Between Modules

Modules talk in two ways only (AD-01, {{nfr-modular}}).

  1. Public service contract. A module that needs an answer from another module calls an interface in that module's Contracts folder, for example AchievementRecordService::isComplete(). The interface returns DTOs or scalars, never Eloquent models.
  2. Domain event. A module that needs to tell others what happened raises an event. Listeners in other modules react. Events are named in the past tense and listed in Sections 4 and 6.

Rules of inter-module communication

Note: Credential issuing after completion is the one place where an event starts automatic work. CompletionConfirmed (EV-31) starts the issue job because the deputy dean's confirmation is itself the decision ({{br-verifyfirst}}). Nothing else is issued without a human decision.

2.6 Transactions and Events

Each action runs in one database transaction so that a multi-record change succeeds or fails as a whole ({{nfr-transactions}}). Inside the transaction an action locks the row it changes, checks the rule, saves, and writes the audit row. After the commit the events fire and jobs are queued. A job is idempotent: it can run twice without a second result, using the record's identifier as the idempotency key ({{ir-idempotent}}). Registration takes a row lock on the offering to keep capacity exact under concurrent submissions ({{nfr-capacity}}).

2.7 Adapter Pattern

Each external system has a PHP interface in MD-16 and three implementations (AD-08, {{ir-adapter}}, {{ir-stubs}}). The configuration for the environment chooses which one is bound in the service container, so a business module never knows which one it is using ({{ir-mode}}, {{nfr-config}}).

3.5 Internationalisation

Interface text is bilingual (AD-13, {{fr-lang}}, {{ir-lang}}).

  • Lang files. Each module keeps Resources/lang/ms/<module>.php and en/<module>.php, loaded under the namespace of the module, for example __('assessment::results.verify_title'). Shared strings are in lang/. A test fails if a key exists in one language and not the other. Bahasa Melayu terms follow the Guide ({{nfr-bmterms}}).
  • Locale per user. The locale is stored in the user's profile and held in the session. The language switch posts to the same page and keeps entered data ({{nfr-langswitch}}). The public site takes the locale from a query value or cookie, with Bahasa Melayu as the default.
  • Content columns. Text that users see and that belongs to a record is stored in two columns, title_ms and title_en, read through a Bilingual cast that returns the user's language and falls back to the other ({{dr-bilingual}}, {{nfr-bilingualcontent}}). Credentials, notices and documents are produced in the language chosen for them ({{fr-crlang}}, {{fr-ntlang}}).
  • Formats. Helpers in MD-00: Fmt::date() returns DD/MM/YYYY, Fmt::time() returns 24-hour Malaysia time, Fmt::money() returns "RM 450.00" ({{ir-dates}}, {{ir-time}}, {{nfr-currency}}). Dates are stored in UTC and displayed in Asia/Kuala_Lumpur ({{dr-time}}). Names are never shortened or reformatted ({{nfr-names}}).
  • Statuses. Status labels come from the enum label method in both languages, so the same word is used on every screen.

3.6 Configuration and Feature Flags

Environment values (addresses, keys, adapter modes) are configuration, not code ({{nfr-config}}). Secrets come from the environment and are never committed. Business thresholds and lists are versioned settings in the database, not configuration (AD-12).

Configuration files and what they hold

Rules for flags and non-production switches:

  • A flag guards a whole capability (a route group, a menu item, an adapter binding). Code inside a flagged capability is written and tested in Release 1 where practicable, so that turning it on is a configuration change.
  • A Release 2 or 3 switch is off by default. A route behind an off switch returns 404 and its menu item is not drawn.
  • Demo clock. A Clock service in MD-00 returns the current time. In non-production a setting can move it so that expiry alerts and overdue reminders can be shown, as the prototype does. The service provider refuses to boot when APP_ENV=production and the demo clock or the stub identity provider is on (AD-06, AD-18).
  • Code never calls now() directly for a business date; it uses Clock::now(), so tests and the demo clock work.

4. Module Design

This section designs the seventeen modules of MCMS (AD-01). Each module has the same sub-structure: a fact sheet, a table of actions, and, where the module owns a record with a life cycle, a state machine. Section 4.19 collects the domain events (EV-xx) and the jobs (JB-xx) in two catalogues. Section 6 lists the events again and Section 7 shows the main flows as sequences.

4.1 Conventions for Module Descriptions

The following conventions apply to every module in this section.

  • Fact sheet. Purpose, the SRS requirements delivered, the tables owned (snake_case plural, columns defined in Section 5), the screens served by their UI/UX specification ID, the events published and consumed, and the jobs run.
  • Tables owned. Only the owning module reads or writes its tables. Other modules call its public service interface or react to its domain events (AD-01).
  • Actions. An action is one public service operation, called by a Livewire component or a controller. Every action runs under a Laravel Policy that checks role, scope and separation of duties on the record (AD-07). The policy column names the rule that is not obvious from the role alone.
  • Confirmation. "Yes" means the interface shows a confirmation dialog before the action runs ({{ir-confirm}}). An action with "Yes" is irreversible, submits, approves, issues, revokes or changes a setting. The server does not rely on the dialog: it checks the same rules again.
  • Roles. Student (P8), Lecturer (P1), Deputy dean of the PTj (P2), colleague reviewer (X1), industry expert (X2), public verifier (X3), CODL system administrator (S1) and CODL technical operator (P5). CODL roles never pass an academic policy (D-12). The Senate has no login: the deputy dean records each Senate decision with its meeting reference (D-11).
  • Audit. Every action that changes a record writes an audit_events row in the same database transaction (AD-11). The tables in this section do not repeat this.
  • No deletion. A correction creates a new revision linked to the old record. No module offers a delete action on a business record (D-20, {{dr-nodelete}}).
  • Events. A service publishes an event after its transaction commits (afterCommit). Listeners are queued on the default queue and are idempotent: each listener stores the event ID it has handled. Events carry record IDs and version numbers, not personal data. Event names are PastTense class names.
  • Jobs. Every job has a queue, an idempotency key and a retry rule (Section 4.19). A job that exhausts its retries writes an integration_jobs row in the failed state and raises AdapterCallFailed or a module-specific failure event.
  • State machines. Status words are those of UI/UX Specification v1.1 section 4.8. Each transition names the action that causes it. A state change is made only by the owning module's service.
  • Derived wording. Credit, MQF level and QV wording is read from verified records at the time of use and is never typed or stored as free text (D-17, {{dr-derived}}).

4.19.1 Domain events

The event IDs below are final for this document. Section 6 and Section 7 reuse them. Cross-module reactions that matter most are:

4.19.2 Jobs

Queues are named in AD-05: default, notifications, imports, credentials, reports, integration and default. Scheduled jobs are started by the Laravel scheduler and dispatch to a queue. Long jobs report progress in job_runs. Alert jobs record each sent alert in alert_log so a re-run sends nothing twice. The idempotency key is stored on the job record, and a second run with the same key does nothing. Retry delays grow at each attempt (backoff).

5.3 Status Enumerations

Statuses use exactly the words of UI/UX Specification v1.1, Section 4.8. In PHP each status is a string-backed enum under app/Modules/<Module>/Enums. The case name is the PascalCase of the label, and the stored value is the snake_case of the label, with brackets removed (for example Held (integrity) is case HeldIntegrity, stored as held_integrity). The label shown to the user comes from the lang file key status.<stored value> in Bahasa Melayu and English (AD-13). The label is never stored. Negative statuses are tested before positive ones in policies and views, so "Not approved" is never read as an approval.

Status enumerations (UI/UX Specification Section 4.8)

Notes on the use of these enums:

  • Result and module status. One enum serves both columns. assessment_results.status allows only Provisional, Verified and Held (integrity). module_enrolments.status allows Not started, In progress, Provisional, Held (integrity) and Achieved. A module becomes Achieved only when its results are Verified ({{fr-asverify}}, {{fr-asmodule}}).
  • Display statuses. A label such as "Completed, waiting for verification" in the prototype is a view-model string built from EnrolmentStatus::Completed and the result status. It is never stored.
  • Deposit outcome. The deputy dean records a deposit outcome of Successful, In process or Correction needed ({{fr-dprecord}}). It is stored in abc_deposits.deposit_status (enum DepositOutcome). Successful sets acrs.status to Deposited, Correction needed sets it to Correction needed, and In process leaves it at Consent given.
  • Public status. The public verification page uses valid, corrected, replaced and revoked ({{fr-vffields}}). The service maps Issued to valid.

5.5 Identifiers

Identifier types

Rules for human references:

  • The format of each kind is held in code, not in settings. The prefix, the width of the number and whether the number restarts each year are fixed per kind. {{tab:data-refs}} lists them.
  • The generator opens a transaction, selects the reference_sequences row for (kind, scope, year) with lockForUpdate, adds one, and writes the record in the same transaction. A rollback undoes the increment, so numbers have no gaps. The year is the year of creation in Asia/Kuala_Lumpur.
  • A reference has a unique index on its table. A reference is never reused or edited. Human references carry no secret; access is always decided by a policy and never by knowing the number ({{sr-authz}}).

Human reference formats

The prototype shows verification codes as eight characters in two groups (3HXP-92LD). The design uses ten characters, as AD-09 states. The page groups them for reading (3HXP9-2LDKQ). On input, the service removes hyphens and spaces, upper-cases the text and maps the letters I and L to 1 and O to 0, as Crockford base32 allows. The alphabet has no I, L, O or U. A new code is generated until the unique index accepts it.

5.6 Audit Design

The audit trail satisfies {{fr-auditlog}}, {{fr-auditview}}, {{sr-tamper}} and AD-11. It records every approval and decision, credential action, result change, ACR, deposit, transfer and redemption status change, role and setting change, correction and disposal. A single AuditLog::record() call writes a row. Business code never writes audit_events directly.

5.6.1 Columns

Columns of audit_events

5.6.2 Hash Chain and Transaction Rule

  • Hash. hash = SHA-256(prev_hash + canonical_json(row)). The canonical JSON has the columns in fixed order (seq, occurred_at in UTC ISO 8601 with microseconds, actor_id, actor_role, action, subject_type, subject_id, before, after, reason, external_ref, context), keys sorted, no spaces, UTF-8.
  • Same transaction. AuditLog::record() must run inside the database transaction of the change it describes. If no transaction is open it throws. The row and the change commit together or not at all.
  • Serialising. The call locks the single audit_chain_heads row (lockForUpdate), reads last_seq and last_hash, writes the new row, and updates the head, all in the caller's transaction. This uses only Eloquent features and so works on PostgreSQL and MySQL (AD-03). Audit writes are therefore serial. At the Release 1 volume (the peak of {{nfr-peak}} is 2,000 registrations in 2 hours) a short lock is acceptable. Section 9 holds the load figures.
  • Database role. The application connects as mcms_app, which has INSERT and SELECT on audit_events and no UPDATE, DELETE or TRUNCATE. Migrations run as a different role, mcms_migrator. A trigger that raises an error on UPDATE and DELETE of audit_events is added in a migration as a second barrier ({{sr-tamper}}).
  • Integrity check job. A scheduled job (JB-18, VerifyAuditChainJob) runs every night at 02:00. It reads rows after audit_chain_heads.verified_seq in order, recomputes each hash and checks the link to the previous row, then moves verified_seq and verified_hash forward. It also recomputes the whole chain once a month. A mismatch writes a security log entry and an alert to the system administrator ({{sr-alerts}}). The audit screen (CODL-10) and the audit export (DOC-16) show an integrity line with the last verified sequence and time.
  • Reading. The audit views filter by subject, actor and date. Staff see only entries of records in their scope ({{fr-auditview}}).

5.7 Versioned Settings

A setting is a key with a typed value. Its history is kept in setting_versions ({{fr-settings}}, {{fr-settinghist}}, AD-12). A row of setting_versions is never updated or deleted. A change inserts a new row with the new value, an effective_from time (now or in the future), the user and the reason, and points to the row it supersedes.

  • Resolving a value. The value in force at time t is the row of the setting with the largest effective_from not after t. The SettingResolver takes the key and the time, defaulting to now, and returns the value and the id of the version.
  • Decisions store the version. A decision that depends on a setting stores setting_version_id and uses the value of that version for ever ({{dr-asof}}). {{tab:data-settinguse}} lists them.
  • Calculated alerts (for example QV expiry at 180, 90 and 30 days) use the value in force on the day the scheduler runs. They are not decisions.
  • Audit. A setting change writes an audit row with the old and new values and the reason. Confirmation is required in the dialog ({{ir-confirm}}).

Decisions that store a setting version

Settings are cached per request. The cache key includes the latest setting_versions.id of the setting, so a new version is used at once on every node ({{nfr-stateless}}).

5.8 Bilingual Content

Text that a participant sees is stored in Bahasa Melayu and English ({{dr-bilingual}}, {{nfr-bilingualcontent}}, AD-13). Each such field is a pair of columns with the suffixes _ms and _en.

  • Fields. Names and descriptions of micro-credentials versions, learning outcomes, modules and assessment components, programme and PTj names, readiness item labels, the recognition statement, and the subject and body of every template version.
  • Draft state. While a version is a draft, one language may be empty. The form marks the missing language ({{fr-lang}}). The submit check and the publish check for templates both require both languages. A template version cannot be published with a missing language.
  • Reading. The HasBilingualAttributes trait gives $model->title in the locale of the user, and falls back to the other language only on staff screens, marked as a fallback. Participant documents and credentials show both languages, with BM beneath EN ({{fr-crlang}}).
  • Locale. users.locale holds ms or en. A notification stores its rendered subject and body in the recipient's locale at creation, and the template version used.
  • Search. The full-text vector of a bilingual field concatenates both languages, using the simple text search configuration, so that no stemming of one language damages the other.

5.10 Retention and Archiving

Retention periods are open (A-08, OI-07). The design stores one setting per record category, retention.<category>, with the value TBD until OI-07 is closed ({{fr-retention}}, {{nfr-records}}). Retention by record category (periods are placeholders)

  • Archiving. Archiving means the record leaves default lists and searches. A record past its active period is shown only through the traceability and report screens (Section 4, MD-15).   • Disposal. A disposal request names a category and a cut-off date. 6.2.1 Microsoft Entra ID (OpenID Connect)

6.2.8 Public Verification Page and JSON API

Verification endpoints

Rules for the response:

  • Fields. Only the holder's name, the credential name, the issuer, the issue date and the status (valid, corrected, replaced, revoked), plus any field listed in the setting verification.public_fields ({{fr-vffields}}). No identity card or passport number, matric number, email address or result is ever returned.
  • Lookup. The code is normalised (Section 5.5) and looked up by the unique public_code. A revoked credential still answers with status revoked. A credential that was corrected or replaced answers with that status and no link to the new credential.
  • Not found. An unknown or malformed code returns HTTP 404 with the same neutral body in every case: no hint whether a similar code exists ({{fr-vfnotfound}}). The code in the URL is never echoed in the body.
  • Rate limit. Verification and catalogue routes are limited by network address with Laravel's rate limiter ({{sr-ratelimit}}). A stricter limit applies to not-found answers, which are the signature of code guessing. Above the limit the response is HTTP 429 with a Retry-After header. The limits are configuration values (a DA is proposed in the report).
  • Logging. Each request writes a verification_logs row with the time, the credential (when found), the outcome and the network address. A not-found request stores a hash of the code, not the code ({{fr-vflog}}).
  • Headers. Cache-Control: no-store so a revocation is visible at once. The page has no cookies and no scripts from other sites.
  • File check. A verifier may upload a Digital Credential file. The page checks its signature against the published key and compares it with the stored payload hash ({{fr-vfsignature}}). The file is not stored.

7.12 Job Designs

All background work runs as Laravel queued jobs on Redis under Horizon (AD-05, {{nfr-queue}}). The scheduler starts timed jobs ({{nfr-scheduler}}). Rules common to all jobs:

  • A job is idempotent. It records its natural key before it acts, and a second run with the same key returns the first result.
  • A job is retried with a growing delay (for example 1, 5, 15 and 60 minutes) up to a set number of tries. When tries are exhausted the job moves to the failed-job list, and an alert is sent to CODL ({{fr-ihretry}}).
  • A job never holds a database transaction while it calls an external service. It reads, calls, then writes in a short transaction.
  • A job writes progress to a job_runs row (total, done, failed, status). The screen polls that row.
  • A failure of one item does not stop the others. Failures are listed with a reason.

8. Security and Privacy Design

This section describes how MCMS meets the security requirements {{sr-sso}} to {{sr-pentest}} and the privacy requirements under the Personal Data Protection Act 2010 (PDPA). The target is OWASP ASVS Level 2 ({{sr-asvs}}). Terms of the architecture decisions AD-06, AD-07, AD-09, AD-11 and AD-14 apply.

8.1 Authentication and Sessions

  • Sign-in. Staff and students sign in with Microsoft Entra ID through OpenID Connect and Laravel Socialite (AD-06, {{fr-sso}}). MCMS has no password store and no public sign-up ({{fr-nosignup}}). The authorisation-code flow with PKCE is used. The state and nonce values are checked, and the ID token signature, issuer, audience and expiry are validated.
  • First sign-in. A profile is created from the token claims and the Participant role is assigned ({{fr-firstlogin}}). Outside applicants are recognised by an attribute or an import ({{fr-applicant}}).
  • MFA. Multi-factor authentication for staff roles is enforced by Entra Conditional Access ({{sr-mfa}}). MCMS also checks the amr claim at sign-in. If a user holds a staff role and amr does not contain an MFA method, the session is created without the staff roles and the user is told to complete MFA. The check is repeated when a staff role is assigned.
  • Session. A server-side session is stored in Redis with a rotated session ID at sign-in. The cookie has the Secure, HttpOnly and SameSite=Lax attributes. The idle timeout is 30 minutes and is the setting auth.idle_timeout_minutes ({{fr-session}}). The session also has an absolute lifetime. Sign-out ends the session on the server.
  • Stub identity provider. The stub sign-in ({{fr-devidp}}) is registered only when APP_ENV is not production. A boot check refuses to start the application in production if the stub is enabled, and a test in the pipeline fails if the stub route exists in a production configuration.
  • Deactivation. A deactivated account cannot sign in and its sessions are removed. Linked records are kept ({{fr-userlist}}).
  • Transport. All traffic uses TLS 1.2 or higher ({{sr-tls}}, {{ir-https}}), with HSTS.

8.2 Authorisation Design

Every action is checked on the server ({{sr-authz}}, {{fr-rbac}}). Hiding a button is a convenience and not a control. Authorisation is built from three rules, applied by one Laravel Policy per record type (AD-07).

  1. Role. The user holds a role that may take the action ({{fr-multirole}}).
  2. Scope. The role assignment carries a scope: the whole University, a PTj, or a list of micro-credentials ({{fr-scope}}). A record outside the scope is not shown and not found by search (AD-16).
  3. Separation of duties on the record. The policy loads the record and compares it with the actor ({{fr-sod}}): a proposer cannot review or decide their own proposal, a person who entered a result cannot be its only verifier, and a reviewer who declared a conflict cannot open the review ({{fr-coi}}).

CODL roles (S1 and P5) never pass an academic policy, and there is no super-user bypass for an academic action (D-12, {{fr-adminlimits}}). The approving roles for each decision type come from the setting approval.route.*, which is versioned ({{fr-approverbody}}, AD-12). Role assignment needs a reason and an effective date and is audited ({{fr-roleassign}}). Least privilege applies to database roles and to staff accounts ({{sr-leastpriv}}), and roles are reviewed on a schedule ({{sr-review}}).

8.4 Secrets and Key Management

  • Application secrets (database, Redis, SMTP, OIDC client secret, storage keys) are environment variables supplied at deployment from a secret store. They are not in the repository and not in logs. Each environment has its own set.
  • Credential signing keys. Credentials are signed with Ed25519 (AD-09). The private key is held in a key vault owned by CODL, and the application calls the vault to sign and never sees the private key in plain text ({{sr-keys}}, {{ir-hsm}}). If the vault is not available, issuing waits and nothing is signed with another key.
  • Key identifiers. Each credential stores the key ID of the key that signed it, as the verification method in its proof. The public keys are published at a fixed URL as a controller document so that anyone can verify a credential.
  • Rotation. A new key pair is created on a schedule or when compromise is suspected. New credentials use the new key from its start date. Old public keys stay published so that earlier credentials still verify. A compromised key is marked revoked with a date, and the affected credentials are listed by key ID for a decision on replacement.
  • Separate keys per environment. Test and staging keys are different from production keys, and credentials signed in those environments say so in the issuer metadata.
  • Backups of data are encrypted, and access to them is limited ({{sr-backupprotect}}). Encryption at rest is used for the database volume and the object store.

8.5 Audit Integrity

The audit trail is an append-only table (AD-11, {{fr-auditlog}}, {{sr-tamper}}, {{dr-immutable}}).

  • The application database role has INSERT and SELECT only on audit_events. It has no UPDATE and no DELETE. A migration role used only at deployment owns the table.
  • Each row stores the hash of the previous row and its own hash, computed over the previous hash and the canonical row content (actor, action, record type and ID, before and after summary, reason, time). Rows are chained in one global sequence.
  • The audit row is written in the same transaction as the change it records, so a change without an audit row cannot be committed ({{br-audit}}).
  • A verification job (VerifyAuditChainJob (JB-18), section 7.12) recomputes the chain every night. A break raises a security alert at once ({{sr-alerts}}), and the job never repairs the chain.
  • The head hash is copied each day to a store the application cannot write to, such as a log server, so that deletion of the tail can be seen.
  • Corrections are new rows. Earlier rows are never changed ({{fr-correct}}, D-20). Viewing the trail is limited to the user's scope ({{fr-auditview}}).

8.6 Public Surfaces

The public surfaces are the catalogue and the credential verification page and API ({{fr-vfpage}}).

  • Minimum fields. The page shows only the permitted fields ({{fr-vffields}}), set by verification.public_fields: status, credential title, issuer, issue date, category, and credit, MQF and QV only when verified. It never shows identity numbers, matric numbers, email or results.
  • No enumeration. The verification code is a random 10-character string from a cryptographic generator, so codes cannot be guessed from sequence or from other data (DR-07, {{dr-publicid}}). Internal IDs are ULIDs and are not used on public pages.
  • Not found. An unknown or malformed code returns the same message, the same status code and similar response time ({{fr-vfnotfound}}). It never suggests a similar code.
  • Rate limiting. Requests are limited per IP address by Laravel's rate limiter, with a stricter limit on failed lookups, so that bulk guessing is impractical ({{sr-ratelimit}}). Limited requests get a neutral message.
  • Logging. Each lookup logs time, code and outcome, and the IP address only ({{fr-vflog}}). No other personal data is logged.
  • Availability. The page reads from a small projection so it stays fast ({{nfr-verify}}, {{nfr-verifyavail}}).
  • Caching. The page is not cached by shared caches, so a revocation shows at once.

8.8 Security Logging and Alerting

Security events are written to the application log in a structured form, separate from the audit trail ({{sr-seclog}}, {{nfr-applog}}). The events are:

  • Sign-in success and failure, MFA failure, role-less staff sessions, and sign-out.
  • Authorisation denials (policy refusals), with actor, action and record type.
  • Role assignment and revocation, and setting changes.
  • Failed verification lookups and rate-limit hits.
  • File upload rejections and virus detections.
  • Key vault use and failures, and key rotation.
