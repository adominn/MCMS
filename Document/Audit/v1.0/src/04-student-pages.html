3. Student / Learner Pages & Functionality Analysis

The Student role (Persona P8) represents enrolled and prospective learners. The student interface prioritizes active coursework, verifiable achievements, Malaysian Qualifications Agency (MQA) credit recognition, and stackable pathways toward formal academic qualifications.

3.1 Student Home: "My Learning" Dashboard

A. Page Information

  • Page Name: Student Home ("My Learning")
  • Role: Student (student)
  • Exact Route: GET /tasks (redirected internally by TaskController@index)
  • Page Type: User Dashboard / Learning Command Center
  • Related Database Tables: enrolments, offerings, mc_versions, mc_modules, module_achievements, credentials, acrs, transfer_applications
  • Related Components & Controllers: App\Modules\Identity\TaskController@student, View: student.home

B. Intended Functionality

Provides an immediate, summary-first overview of the student's academic journey. Features: (1) Urgent action items (pending consent, feedback requests, payment deadlines), (2) In-progress courses with module completion progress bars, (3) Courses waiting for Deputy Dean completion confirmation, (4) Recently achieved credentials, and (5) KPI summary metrics (Achieved Modules, Issued Credentials, Pending ACR Consents, Active Transfer Applications).

C. Current Implementation

Fully implemented and tested by Playwright flow FL-00. Dynamically calculates module completion percentages by correlating mc_modules with module_achievements. Empty states provide quick links to the public catalogue.

D. Functionality Status

Status: Fully Working. Data aggregation across 8 tables executes efficiently without N+1 query regressions.

3.2 Course Registration Wizard & Payments (MD-05)

A. Page Information

  • Page Names: Registration Wizard (/register/{offering}), Confirmation (/enrolments/{id}/confirmation), Receipt (/enrolments/{id}/receipt), Withdrawal (POST /enrolments/{id}/withdraw)
  • Role: Student (student)
  • Exact Routes: GET /register/{offering}, POST /register/{offering}/eligibility, POST /register/{offering}/acknowledge, POST /register/{offering}/pay, GET /enrolments/{id}/confirmation, GET /enrolments/{id}/receipt
  • Page Type: Multi-Step Form & Payment Gateway
  • Related Database Tables: enrolments, payments, pdpa_acknowledgements, offerings, enrolment_status_log
  • Related Components & Controllers: App\Modules\Enrolment\EnrolmentController, Views: student.register, student.confirmation, student.receipt

B. Intended Functionality

Implements a 4-step compliant enrollment workflow (FR-97 to FR-109): (1) Eligibility & Contact: Validates prerequisites and emergency phone number; (2) Recognition & PDPA Acknowledgment: Mandatory acceptance of Personal Data Protection Act notice and official recognition statements; (3) Payment Processing: Idempotent fee handling with payment simulation; (4) Confirmation: Enrolment reference (e.g., E-2026-0590), downloadable receipt, and access instructions.

C. Current Implementation

Fully functional and verified in Playwright flows FL-06 and FL-06b. Card details are never stored; payment attempts utilize unique UUID references. The enrollment receipt adheres to the standard A4 print layout (layouts.print).

D. Functionality Status

Status: Fully Working. Validations, status transitions (pending_payment → enrolled), capacity counting, and withdrawal deadlines (20 days before cohort completion) are enforced.

3.3 Results & Internal Achievement Record (MD-07, MD-08)

A. Page Information

  • Page Names: My Results (/my-results), Internal Achievement Record (/my-record)
  • Role: Student (student)
  • Exact Routes: GET /my-results, GET /my-record
  • Page Type: Academic Results & Internal Transcript
  • Related Database Tables: enrolments, assessment_results, assessment_components, module_achievements, digital_badges, achievement_records
  • Related Components & Controllers: ResultsController@mine, RecordController@mine, Views: student.results, records.mine

B. Intended Functionality

Displays verified assessment results per cohort and module. /my-results breaks down component marks (quizzes, assignments, exams) and shows earned module badges. /my-record renders the official internal Achievement Record (DOC-05). In accordance with BR-12, the Achievement Record is prominently watermarked and labeled: "Internal Academic Record – Not an Academic Credit Record (ACR)."

C. Current Implementation

Strictly enforces that students only see marks that have been formally verified by the Deputy Dean (FR-128); unverified marks entered by lecturers remain hidden. Results under integrity holds display a neutral pending notice.

D. Functionality Status

Status: Fully Working. Tested in Playwright flow FL-08.

3.4 Digital Credentials Wallet & Certificate Print (MD-09)

A. Page Information

  • Page Names: Credentials Wallet (/my-credentials), Credential Detail (/my-credentials/{id}), Certificate (/my-credentials/{id}/certificate), Transcript Sheet (/my-credentials/{id}/sheet), Download (/my-credentials/{id}/download/{as})
  • Role: Student (student)
  • Exact Routes: GET /my-credentials, GET /my-credentials/{id}, GET /my-credentials/{id}/certificate, GET /my-credentials/{id}/sheet, GET /my-credentials/{id}/download/{as}
  • Page Type: Credential Wallet / Printable Certificate / File Export
  • Related Database Tables: credentials, enrolments, signing_keys, mc_versions
  • Related Components & Controllers: CredentialController, Views: credentials.wallet, credentials.show, credentials.certificate, credentials.sheet

B. Intended Functionality

The student's portable credential repository (FR-137 to FR-147). Upon cohort completion confirmed by the Deputy Dean, the system automatically mints a tamper-evident credential. From the wallet, learners can: (1) View verification status, (2) Copy public verification links, (3) Download the VC-JWT / Open Badges 3.0 cryptographic package, (4) Print the official bilingual A4 Certificate with QR code and signatories, and (5) Inspect the academic transcript sheet.

C. Current Implementation

Fully implemented and aligned with the prototype. The certificate page (layouts.print) renders institutional letterheads, signatory blocks, and dynamic SVG QR codes encoding the public verification URL. Cryptographic downloads provide compliant VC-JWT files signed with Ed25519.

D. Functionality Status

Status: Fully Working. Issuance, certificate formatting, and token downloads validated by FL-09 and FL-10.

3.5 Credit Ledger, ACR & National Credit Banking (MD-11)

A. Page Information

  • Page Names: Credit Ledger (/my-credit), ACR & Consent Review (/my-credit/{id}), Submit Consent (POST /my-credit/{id}/consent)
  • Role: Student (student)
  • Exact Routes: GET /my-credit, GET /my-credit/{id}, POST /my-credit/{id}/consent
  • Page Type: Financial/Academic Ledger & Legal Consent
  • Related Database Tables: acrs, consents, credit_ledger_entries, abc_deposits, redemption_events
  • Related Components & Controllers: CreditBankController, Views: creditbank.ledger, creditbank.acr

B. Intended Functionality

Empowers students to manage credits banked with the Malaysian Academic Credit Bank (ABC). An Academic Credit Record (ACR) is automatically generated only for accredited UMCs or verified SAMCs (never MCEs). Before credit can be queued or exported to ABC, the student must review the generated ACR and submit legal consent (FR-dp*). Once deposited by the Deputy Dean, credits appear in the ledger with a 10-year validity counter.

C. Current Implementation

Fully implemented. Consent submission stores channel, timestamp, and version of wording. The ledger clearly distinguishes between Available, Provisionally Redeemed (in transfer evaluation), Redeemed, and Expired credits. Every screen clearly emphasizes that an ABC deposit is secure storage, not an automatic credit transfer.

D. Functionality Status

Status: Fully Working. Tested in Playwright flow FL-11.

3.6 Credit Transfer Applications & Degree Plan (MD-12, MD-13)

A. Page Information

  • Page Names: Credit Transfer Listing (/transfer), New Application (/transfer/new), Application Detail (/transfer/{id}), Degree Plan (/my-plan)
  • Role: Student (student)
  • Exact Routes: GET /transfer, GET /transfer/new, POST /transfer, GET /transfer/{id}, GET /my-plan
  • Page Type: Application Workflow & Interactive Degree Tracking
  • Related Database Tables: transfer_applications, transfer_lines, programmes, stackable_plans, plan_requirements, credit_ledger_entries
  • Related Components & Controllers: TransferController, PathwayController@mine, Views: transfer.index, transfer.create, transfer.show, pathways.mine

B. Intended Functionality

Allows learners holding Available credits to formally apply for credit transfer toward a target UTeM academic degree programme. The application enforces single redemption (BR-26): applied credits are immediately placed on hold as Provisionally Redeemed. /my-plan tracks the student's progress along stackable pathway mappings, calculating the percentage of institutional credit earned against the 30% residency rule.

C. Current Implementation

Fully functional. Application creation verifies that selected credits are unencumbered. Once submitted, the application enters the faculty Deputy Dean evaluation queue. The student can track evaluation milestones (Validity Check → Equivalence Review → Senate Decision). /my-plan visually flags missing programme requirements and residency ratios.

D. Functionality Status

Status: Fully Working. Single redemption locking and status tracking verified in FL-12 and FL-13.

3.7 Course & Cohort Feedback Form (MD-14)

A. Page Information

  • Page Names: Feedback Hub (/feedback), Cohort Feedback Form (/feedback/{enrolment})
  • Role: Student (student)
  • Exact Routes: GET /feedback, GET /feedback/{enrolment}, POST /feedback/{enrolment}
  • Page Type: Survey Form & Learner Evaluation
  • Related Database Tables: feedback_responses, enrolments, offerings
  • Related Components & Controllers: App\Modules\Monitoring\QualityReviewController, Views: monitoring.feedback, monitoring.feedback-form

B. Intended Functionality

Collects mandatory quality feedback from participants upon cohort completion or closure (FR-mn*). The evaluation comprises 18 items grouped into 6 quality domains: (1) Learning Outcomes & Content, (2) Delivery & Activities, (3) Assessment & Feedback, (4) Platform & Accessibility, (5) Facilitator Support, and (6) Overall Satisfaction. Responses are completely anonymized to protect participant privacy.

C. Current Implementation

Fully implemented. Enforces one submission per enrollment. The 6 core group ratings are strictly validated as required, while the 12 detailed diagnostic items are optional. Completed surveys feed directly into lecturer CQI aggregate indicators.

D. Functionality Status

Status: Fully Working. Verified in unit tests and manual execution.
