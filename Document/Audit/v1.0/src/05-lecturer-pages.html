4. Lecturer / Educator Pages & Functionality Analysis

The Lecturer role (Persona P1) represents academic curriculum developers, course coordinators, and instructors. Lecturers author micro-credential proposals, manage version transitions, supervise cohort deliveries, enter student assessment marks, assemble Quality Verification portfolios, and execute Continuous Quality Improvement (CQI) cycles.

4.1 Lecturer Dashboard & Work Queue

A. Page Information

  • Page Name: Lecturer Dashboard & Work Tasks
  • Role: Lecturer (lecturer)
  • Exact Route: GET /tasks (with active lecturer role)
  • Page Type: Work Queue / KPI Hub
  • Related Database Tables: tasks, micro_credentials, mc_versions, offerings
  • Related Components & Controllers: App\Modules\Identity\TaskController@index, View: tasks

B. Intended Functionality

Provides an immediate action-oriented overview of pending academic responsibilities. Displays KPI cards: (1) Approved micro-credentials, (2) Proposals in review or pending endorsement, (3) Active draft proposals, and (4) Open/upcoming offerings. Lists overdue tasks (e.g., mark entry deadlines, CQI action reviews, readiness checklists) with area filtering.

C. Current Implementation

Fully functional and aligned with prototype screen #/lec/home. Displays lecturer-specific KPIs via lecturerKpis() method. Tasks link directly to corresponding action pages.

D. Functionality Status

Status: Fully Working. Dynamic KPI calculations and task filtering operate correctly.

4.2 Curriculum Proposals & Guided Category Wizard (MD-02)

A. Page Information

  • Page Names: Guided Category Wizard (/proposals/new), My Proposals (/proposals), Proposal Workspace (/proposals/{id}), Printable Proposal (/proposals/{id}/print)
  • Role: Lecturer (lecturer)
  • Exact Routes: GET /proposals, GET /proposals/new, POST /proposals, GET /proposals/{id}, PUT /proposals/{id}, POST /proposals/{id}/submit, GET /proposals/{id}/print
  • Page Type: Multi-Step Wizard & 8-Tab High-Density Authoring Workspace
  • Related Database Tables: micro_credentials, mc_versions, mc_modules, learning_outcomes, assessment_components, assessment_component_outcomes, parent_courses, proposal_readiness
  • Related Components & Controllers: App\Modules\Curriculum\ProposalController, Views: curriculum.new, curriculum.index, curriculum.workspace, curriculum.print

B. Intended Functionality

Guides lecturers through compliant micro-credential development: (1) Category Wizard: A 3-question diagnostic tool that automatically recommends the appropriate category (SAMC, UMC, or MCE) based on credit intent, stand-alone nature, and SLT hours. (2) 8-Tab Workspace: - Basics: Title, description, delivery mode, language. - Justification: Industry demand, target market, stakeholder consultation. - Modules: Breakdown of modular units; for UMCs, parent course selection and unbundling model (credit-based or topic-based). - Outcomes: Malaysian Qualifications Agency (MQA) aligned Course Learning Outcomes (CLOs). - Assessment: Formative/summative assessments with component weights, pass marks, and an alignment matrix mapping each component to assessed modules and CLOs. - Credential: Proposed MQF level, credit value, badge metadata, and expiry terms. - Readiness: Preliminary faculty and platform resource confirmation. - Submit: Live validation engine checking for blocking errors (e.g., total SLT mismatch, missing outcome mappings) and final formal submission to the Deputy Dean.

C. Current Implementation

Fully functional and verified in Playwright flow FL-02 and demonstration scenario Act 1. Live validation checks enforce that SLT totals match contact hours, that every module has at least one assessed component, and that unbundling models adhere to parent course rules. Submitting locks the proposal, transitions version status to submitted, logs an audit event, and dispatches a task to the Deputy Dean.

D. Functionality Status

Status: Fully Working. Workspace tabs, autosave, live validation, and submission locking operate reliably.

4.3 Version Management & Material Changes (MD-02)

A. Page Information

  • Page Names: My Micro-Credentials (/my-mcs), Version History (/my-mcs/{id}), Request Change Form (/my-mcs/{id}/change)
  • Role: Lecturer (lecturer)
  • Exact Routes: GET /my-mcs, GET /my-mcs/{id}, GET /my-mcs/{id}/change, POST /my-mcs/{id}/change, POST /my-mcs/{id}/reoffer
  • Page Type: Version Governance & Change Classification Form
  • Related Database Tables: micro_credentials, mc_versions, change_requests, version_transition_rules
  • Related Components & Controllers: App\Modules\Curriculum\VersionController, Views: curriculum.mcs.index, curriculum.mcs.show, curriculum.mcs.change

B. Intended Functionality

Manages the lifecycle of approved micro-credentials across multiple version iterations (FR-74 to FR-82). Lecturers can request curriculum modifications. The system automatically classifies requested changes from an 11-item checklist into: (1) Minor Change: Typo fixes, reading list updates; requires only Deputy Dean acknowledgment. (2) Material Change: Alterations to outcomes, assessment structure, SLT, credits, or MQF level; creates a new draft version copied from the approved version, requiring full colleague re-review and Senate endorsement.

C. Current Implementation

Fully implemented. Material changes correctly branch into new version drafts (e.g., v1.0 → v2.0-draft). When Senate approves the new version, transition rules (teach-out current students or migrate to new version) are recorded. Re-offer functionality allows launching new cohorts from an approved version without modifying curriculum content.

D. Functionality Status

Status: Fully Working. Change classification, version branching, and transition rule logging operate correctly.

4.4 Course Offerings (Cohorts) & Readiness Checklist (MD-04)

A. Page Information

  • Page Names: Offerings Listing (/offerings), Create Cohort (/offerings/new), Offering Delivery Dashboard (/offerings/{id}), Participants Roster (/offerings/{id}/participants), Readiness Checklist (/offerings/{id}/readiness)
  • Role: Lecturer (lecturer)
  • Exact Routes: GET /offerings, GET /offerings/new, POST /offerings, GET /offerings/{id}, GET /offerings/{id}/participants, GET /offerings/{id}/readiness, POST /offerings/{id}/readiness
  • Page Type: Cohort Management, Stepped Checklist & Learner Roster
  • Related Database Tables: offerings, readiness_items, readiness_confirmations, enrolments, mc_versions, ucreds_courses
  • Related Components & Controllers: App\Modules\Offering\OfferingController, Views: offerings.index, offerings.new, offerings.show, offerings.participants

B. Intended Functionality

Enables lecturers to instantiate and manage delivery cohorts for Senate-approved micro-credentials. Lecturers define cohort names (e.g., DS-2027-1), start/end dates, max quota, and link the course to UCreds reference courses. Before enrollment can open, the lecturer must complete the comprehensive Readiness Checklist (Appendix B2-B7) verifying LMS course setup, instructor availability, assessment readiness, and student support materials.

C. Current Implementation

Fully functional. Cohort creation validates that the parent version is approved. The readiness checklist captures lecturer responses and evidentiary notes. Completing the checklist transitions cohort readiness to submitted and dispatches a confirmation task to the Deputy Dean.

D. Functionality Status

Status: Partially Working (By Design). The checklist logic, status transitions, and participant rosters work completely. However, evidence attachments currently accept text notes and URLs rather than uploaded binary files (pending object storage service).

4.5 Marks Entry, Integrity Holds & Result Revisions (MD-07)

A. Page Information

  • Page Names: Marks Entry Grid (/results/{offering}), Component Marks Sheet (/results/{offering}/components/{component}), Integrity Case Manager (POST /results/{offering}/integrity), Result Change Request (POST /results/{offering}/change-request)
  • Role: Lecturer (lecturer)
  • Exact Routes: GET /results/{offering}, POST /results/{offering}/marks, POST /results/{offering}/submit, POST /results/{offering}/integrity, POST /results/{offering}/change-request
  • Page Type: High-Density Grade Sheet & Academic Integrity Operations
  • Related Database Tables: assessment_results, assessment_result_revisions, result_change_requests, integrity_cases, enrolments, assessment_components
  • Related Components & Controllers: App\Modules\Assessment\ResultsController, Views: results.cohort

B. Intended Functionality

Allows the course instructor to enter assessment marks for all enrolled participants against approved components (quizzes, lab practicals, final assessments). Features: (1) Component-by-component mark validation (cannot exceed maximum mark), (2) Flagging active academic integrity cases (cheating/plagiarism) which freezes result verification for that learner, and (3) Post-verification grade change requests requiring documented justification and Deputy Dean approval.

C. Current Implementation

Fully functional and verified in Playwright flow FL-08. Raw marks are saved in draft state until the lecturer clicks "Submit Marks for Verification", which locks the grade sheet and forwards the cohort results to the Deputy Dean. Integrity holds successfully isolate affected participants while allowing unaffected participants to proceed.

D. Functionality Status

Status: Fully Working. Grade validation, integrity locks, and change request audit logging operate reliably.

4.6 Continuous Quality Improvement (CQI) Workspace (MD-14)

A. Page Information

  • Page Names: CQI Workspace (/cqi), Cohort CQI Record (/cqi/{offering}), Create Action (POST /cqi/{offering}/actions), Evaluate Action (POST /cqi/{offering}/actions/{action}/evaluate)
  • Role: Lecturer (lecturer)
  • Exact Routes: GET /cqi, GET /cqi/{offering}, POST /cqi/{offering}/actions, POST /cqi/{offering}/actions/{action}/evaluate
  • Page Type: Quality Audit Workspace & Action Tracking Engine
  • Related Database Tables: cqi_records, quality_domain_checks, cqi_issues, cqi_actions, feedback_responses, offerings
  • Related Components & Controllers: App\Modules\Monitoring\CqiController, Views: monitoring.cqi

B. Intended Functionality

Implements institutional closed-loop quality assurance (FR-cqi*). Following cohort completion, the lecturer must assemble a CQI Record analyzing: (1) Participant feedback aggregates across 6 quality domains, (2) Grade distribution metrics (pass rate, failure rate), (3) Root-cause issue identification, and (4) Action plan with assigned owners, due dates, and success criteria. In subsequent cycles, the lecturer must evaluate the effectiveness of previously implemented actions before closing them.

C. Current Implementation

Fully functional and verified in Playwright flow FL-15. Indicators automatically compute median scores from feedback_responses. Action plans strictly follow the two-party lifecycle: the lecturer prepares actions and evaluates effectiveness, but only the Deputy Dean can formally close an action.

D. Functionality Status

Status: Fully Working. Quality domain metrics, action progression, and evaluation checks are operational.

4.7 Stand-alone SAMC Quality Verification (QV) Portfolio (MD-10)

A. Page Information

  • Page Names: Quality Verification Hub (/quality), SAMC QV Portfolio (/quality/{mc}), Assemble Evidence (POST /quality/{mc}/evidence), Submit QV (POST /quality/{mc}/submit)
  • Role: Lecturer (lecturer)
  • Exact Routes: GET /quality, GET /quality/{mc}, POST /quality/{mc}/evidence, POST /quality/{mc}/submit
  • Page Type: Compliance Portfolio & Evidence Assembly
  • Related Database Tables: qv_records, qv_evidence, micro_credentials, mc_versions
  • Related Components & Controllers: App\Modules\Quality\QvController, Views: quality.index, quality.show

B. Intended Functionality

Supports Malaysian Qualifications Agency (MQA) Quality Verification for Stand-alone Micro-Credentials (SAMC). A stand-alone SAMC cannot carry academic credit unless Quality Verification has been successfully conducted (G 6.3.2). The lecturer assembles the 6 mandatory evidence dimensions (curriculum design, learning resources, assessment mechanism, facilitator credentials, participant evaluation, institutional readiness) and submits the portfolio for faculty endorsement.

C. Current Implementation

Fully functional and verified in Playwright flow FL-14. Validates that the micro-credential is an approved SAMC with completed cohorts. Evidence items link to system records. Once submitted, the record enters the Deputy Dean queue for institutional endorsement.

D. Functionality Status

Status: Partially Working (By Design). Evidence items are captured as system references and notes; the compressed ZIP package download feature (FR-169) produces an index page pending stored-file service implementation.
