2. Public / Guest Pages & Functionality Analysis

The Public / Guest role encompasses all unauthenticated user interactions. This tier is critical for public course discovery, prospective student engagement, employer credential verification, institutional transparency, and authentication entry.

2.1 Public Landing Portal

A. Page Information

  • Page Name: Public Landing Portal / Home
  • Role: Public / Unauthenticated Guest
  • Exact Route: GET /public (Route Name: public.home)
  • Page Type: Landing Page / Marketing & Discovery
  • Related Database Tables: offerings, mc_versions, micro_credentials, ptjs
  • Related Components & Controllers: App\Modules\Offering\CatalogueController@home, View: public.home, Layout: layouts.public

B. Intended Functionality

Serves as the primary institutional showcase for UTeM Micro-Credentials. It displays hero messaging, core statistics (active offerings, total learners, participating faculties), featured micro-credentials categorized by discipline (Computing, Engineering, Technology Management), an explainer on micro-credential stacking, and direct navigation links to the catalogue, verification portal, and degree pathways.

C. Current Implementation

Fully implemented and aligned with prototype screen #/public/home. Displays active course cohorts dynamically retrieved from the database where offerings.status = 'open'. Includes bilingual navigation header, search redirect to catalogue, and responsive feature grids. Empty states are handled gracefully when no cohorts are open.

D. Functionality Status

Status: Fully Working. Dynamic database queries correctly filter active, verified offerings. Fast load times, responsive CSS, and full alignment with D-38 styling directives.

E. User Flow & Workflow Diagram

Entry: User visits root URL / or direct URL /public → Action: Explores featured courses, clicks category pill or "Explore Catalogue" → System: Renders homepage with dynamic counts → Destination: Navigates to /public/catalogue or /public/offering/{id}.

2.2 Public Micro-Credential Catalogue

A. Page Information

  • Page Name: Micro-Credential Course Catalogue
  • Role: Public / Guest & Authenticated Learners
  • Exact Route: GET /public/catalogue (Route Name: public.catalogue)
  • Page Type: Listing / Search & Filter Directory
  • Related Database Tables: offerings, mc_versions, micro_credentials, ptjs, qv_records
  • Related Components & Controllers: App\Modules\Offering\CatalogueController@catalogue, View: public.catalogue

B. Intended Functionality

Allows prospective learners to search, filter, and compare all approved micro-credential offerings. Provides filtering by faculty (PTj), category (SAMC, UMC, MCE), delivery mode (Online, Blended), credit eligibility, and keywords. Displays offering badges indicating MQF level, academic credits, fee (RM), cohort duration, and enrollment deadlines.

C. Current Implementation

Fully functional with real-time keyword search and sidebar filters. Filters dynamically query PostgreSQL using Eloquent. Respects D-38 pagination rules (pager rendered only when records exceed 10). Credit and MQF values are displayed strictly from verified records (FR-150).

D. Functionality Status

Status: Fully Working. Filtering, keyword search, reset actions, and responsive layout are operational and tested by Playwright flow FL-22.

2.5 Public Credential Verification Portal & JWKS

A. Page Information

  • Page Names: Public Verification Portal (/public/verify), Verification Result (/public/verify/{code}), File Check (POST /public/verify/file), JWKS (GET /.well-known/jwks.json)
  • Role: Public / Employers / Verifiers
  • Exact Routes: GET /public/verify, GET /public/verify/{code}, POST /public/verify/file, GET /.well-known/jwks.json
  • Page Type: Verification Portal / Cryptographic Security Endpoint
  • Related Database Tables: credentials, signing_keys, verification_log, enrolments, users
  • Related Components & Controllers: App\Modules\Credentials\VerifyController, Views: public.verify, public.verify-result

B. Intended Functionality

Enables any third-party employer or academic institution to verify the authenticity of a UTeM micro-credential without requiring an account (X3, FR-155 to FR-162). Verification is supported via two mechanisms: (1) Entering an 8-character public verification code (e.g., 7Q2M-K4PA), and (2) Uploading a signed Digital Credential file (VC-JWT). Rate limiting (SR-08) and neutral not-found responses prevent enumeration attacks.

C. Current Implementation

Fully implemented. Lookup by code retrieves the credential, logs the verification attempt in verification_log, and renders the verification badge showing status (Valid, Corrected, Replaced, or Revoked). File upload validates the Ed25519 cryptographic signature against the public key published at /.well-known/jwks.json. Rate limiting (60 requests/minute) is strictly enforced.

D. Functionality Status

Status: Fully Working. Tested by Playwright flow FL-23 and unit tests in CredentialTest.php.

2.6 Authentication Portal & MFA Challenge

A. Page Information

  • Page Names: Sign In Portal (/signin), MFA Challenge (/signin/mfa), Root Redirect (/), Sign Out (POST /signout)
  • Role: Public Guest & Authenticated Users
  • Exact Routes: GET /signin, POST /signin/stub, GET /signin/mfa, POST /signin/mfa, POST /signout
  • Page Type: Authentication & Access Control
  • Related Database Tables: users, role_assignments, sessions, audit_events
  • Related Components & Controllers: App\Modules\Identity\StubSignInController, Views: signin, mfa

B. Intended Functionality

Authenticates system users. Under production requirements (OI-03, SR-01), authentication must integrate with Microsoft Entra ID (UTeM Single Sign-On). In development and demonstration environments, a stub identity provider (FR-05) allows selecting personas. Staff holding privileged decision-making roles (Deputy Dean, CODL Administrator) must complete a second-factor authentication (MFA) step (SR-02).

C. Current Implementation

The stub IdP is fully functional and guarded by config('mcms.stub_idp'). Signing in as a student or lecturer logs in directly; selecting Deputy Dean or CODL Admin redirects to /signin/mfa requiring a 6-digit passcode. Successful authentication regenerates the session, updates last_login_at, and creates an audit record in audit_events.

D. Functionality Status

Status: Partially Working (By Design). The stub IdP and MFA simulator work completely for demonstration and testing, but Microsoft Entra ID integration remains pending external UTeM ICT confirmation (OI-03).
