# MC-ABC System Guidelines (Antigravity 6)

## 1. Handover & Core Directives
- **Primary Goal (D-38)**: Build the UTeM Micro-Credential Management System (MCMS) so that it looks and behaves like the approved clickable prototype (style, arrangement, structure, content) while fully working with a real Laravel backend. Extra features that the prototype lacks are acceptable if required by documents, but must strictly adhere to the same styling/conventions and summary-first presentation.
- **UI Guidelines**: Strictly follow [DESIGN.md](file:///C:/Users/Adomin/Documents/Intern/CODL/MC-ABC%20System%20-%20Antigravity%206/DESIGN.md) (v3 Linear-Precision, light-only, Electric Cobalt `#0052ff`, Deep Cobalt Navy `#0b1a3d` sidebar, `Plus Jakarta Sans`, crisp `#090a0f` card outlines). Refer to [HANDOVER.md](file:///C:/Users/Adomin/Documents/Intern/CODL/MC-ABC%20System%20-%20Antigravity%206/HANDOVER.md) for full project history and status.
- **Prohibition of Generic Icons / Emojis (D-53)**: Never use generic emojis (such as ⏱, 🔒, ⚖️, 💡, 👉, etc.) or arbitrary decorative SVGs in UI views. Rely strictly on Linear-Precision typography, layout geometry, and semantic status tags.
- **Prohibition of Guide & Regulatory Structure References (D-64)**: Never display references to the UTeM Micro-Credential Guide or its internal structure (`Appendix A`–`H`, `Lampiran A`–`H`, `B1.`–`B8.`, `C1.`–`C10.`, `D1.`–`D10.`, `E10`, `F1`–`F11`, `G4`–`G11`, `H4`/`H5`/`H8`/`H9`, `Cl.`, `Klausa`, `Garis Panduan Micro-Credential UTeM`, `m/s 119`) in any user-facing UI label, checklist, heading, button, validation/error message, PDF/printout, receipt, email, or notification. Use plain, self-explanatory wording that makes sense without the guide; keep regulatory traceability strictly in internal docs and code comments.
- **Automated Readiness Verification (D-65)**: Offering readiness uses `ReadinessChecker` for automated system checks plus 15 grouped Assisted/Manual confirmations across 4 collapsible sections.
- **Role Governance Alignment (D-66)**: Deputy Dean (`P2`) endorses MC proposals (within own PTj) and retains faculty operational/quality confirmations (offering readiness, results verification, completion, CQI, QV readiness, suspensions, pathway drafting); CODL (`P5`) verifies endorsed MC proposals, evaluates credit transfers (Step 1 validity + 9-criterion outcome equivalence), and shares Senate minute-recording Secretariat access; Academic Authority / Senate (`P3`) grants final approval on MC proposals, credit transfers, stackable pathways, and record disposal; Deputy Dean views credit transfers in read-only monitor mode only and is separated from Records/ABC deposits (`P6`/`P7`); all 403 rejections render contextual role handoffs with safe return links rather than bare generic denials.
- **Bounded Page & Progressive Disclosure (D-67)**: No page may display unbounded growing content at once. Repeating cards must never embed data tables or per-card search bars. All thresholds live in a single file (`app/config/ui.php`): `12` cards/page desktop (`6` mobile), `0` tables inside cards, `10` initial table rows, `1` global search bar, and `≤ 4` open sections. Every new page or change must pass D-67 before acceptance.
- **Immediate In-Place UI Updates & Scroll/Tab Preservation (D-68)**: Every in-page add, edit, remove, or reorder action (`POST` form returning to the same page) must update the visible DOM immediately via `data-inplace` / `data-autosave` (handled in `app/public/js/mcms.js`), cancel any pending autosave timer before submitting to prevent races, preserve the user's exact scroll position and active `[data-tabs]` tab, prevent double-click duplicates, and auto-focus newly added inputs. Inline scripts inside swappable views must run cleanly even when `document.readyState !== 'loading'` (never rely solely on `DOMContentLoaded`). Any same-page `POST` fallback must restore scroll position and active tab via `sessionStorage`.
- **Scalable Pickers & High-Volume User Design (D-69)**: Always design every user, staff, lecturer, reviewer, student, and course selector for university-wide scale (hundreds/thousands of records). Never use raw `<select>` dropdowns or unbounded checkbox walls for people/entity lists. Use searchable comboboxes / server-filtered autocomplete (capped to 10–15 results per query) with contextual pre-filtering (e.g., own PTj/faculty by default with an optional cross-faculty toggle, and MQF/qualification eligibility where relevant) plus removable selected chips.
- **Information Creation & Dependency Order (D-70)**: Steps, tabs, sections, validation checks, and document sections must strictly follow the order in which information is created. Anything that references, maps, or evaluates information must appear after the place where that information is entered (for example, in the proposal form: `Basic information` → `Justification` → `Learning outcomes` → `Modules` → `Assessment` → `Credential` → `Readiness` → `Comments` → `Submit`). Each dependent tab must state clearly what it needs from earlier tabs and link directly to the prerequisite tab when empty. Check every new page against this rule. Never show the rule number or any guide reference in the UI.
- **Generated Document Layout & Zero-Truncation Rule (D-71)**: All generated/printable documents must extend the shared `layouts/print.blade.php` layout (no standalone HTML print views). Text truncation (`Str::limit`, `array_slice` dropping items, `text-overflow: ellipsis`, `overflow: hidden`, or `white-space: nowrap` on data cells) is strictly prohibited in generated documents — truncation is permitted only in on-screen lists/cards. Multi-page tables repeat `<thead>` automatically. Wide sections switch automatically to A4 Landscape via CSS named pages (`@page a4-landscape`) without a manual orientation button when a table has `>= 6` columns, an alignment/mapping matrix (`data-matrix="1"`) has `>= 4` columns, or portrait column width drops below `28mm` (`105px`), while other pages in the same document stay A4 Portrait. Matrix tables with `> 5` data columns automatically split into sequential horizontal chunks repeating column 1 (`Part X of Y` / `Bahagian X daripada Y`).
- **Generated Document Language Rule (D-72)**: Every generated document supports a clean per-document `EN | BM` selector in `.doc-bar` (`?doc_lang=en|ms`, defaulting to the user's current UI language) handled in `UiLanguage` middleware without changing the user's global session locale. Every document renders 100% in the chosen language with zero mixing of English and Bahasa Melayu for all system-written text (letterhead, headings, column labels, statuses, notices, dates, signature roles). Uploaded files and single-language user-typed fields are rendered as entered without silent machine translation.
- **Inline Table Sort & Shared Toolbar Rule (D-73)**: Sorting always lives in an inline Sort control placed beside the search box inside the shared table toolbar (`.tbar` / `.tbar-sort` in `app/public/js/mcms.js` and `mcms.css`), never as clickable arrow icons in column headers (`<th>` headers stay plain labels). Every list or table with search uses the shared toolbar; non-sortable columns (`Action`, `Select all`, `Download`, `Receipt`, `No.`) and role-hidden columns are excluded. Sorting compares true semantic values (dates by timestamp, numbers numerically, statuses by workflow order, text via `Intl.Collator` with BM/case support), places empty values (`-`/`–`) at the end in both directions, uses a stable row-index tie-breaker, provides field-aware direction wording plus Reset to default, announces changes via `aria-live`, and persists across row navigation (`sessionStorage` for client-enhanced tables, URL query params for server-paginated grids). Check every new table against this rule; never display the rule number in the interface.
- **Unified Search, Filter & Sort Toolbar Rule (D-74)**: Every table or list that can grow has one single-row toolbar containing **Search**, **Filter**, and **Sort** built automatically from its own column headers (`.tbar` in `app/public/js/mcms.js` and `mcms.css`), with no separate filter dropdowns placed outside the toolbar. Search uses a contextual placeholder built from visible searchable headers; Filter offers the right control per column (choice list with live counts for categories/statuses/entities, date range for dates, number range for numeric columns, text match for high-cardinality names), skips non-filterable (`Action`) and single-value columns, renders removable active-filter chips with `Clear all` below the toolbar, and respects role-visible rows/counts. Only short fixed/document summary tables (`data-plain`) or form-input tables are excluded. Check every new table against this rule; never show the rule number in the interface.
- **Pop-Out Warning/Error Toasts & Tabbed Review Workspaces Rule (D-75)**: Every validation error, blocking warning, or alert (`main .status.error`, `main .status.warn`) must pop out as a visible floating toast notification (so users never miss an alert while scrolled down a page), deduplicate repeated identical error messages (e.g., `Rate every item. (7)`), provide a manual `×` dismiss button, and auto-dismiss cleanly after a readable timeout (pausing on hover) on both the floating toast and the top inline banner so alerts never linger indefinitely. Multi-section review workspaces (such as Review a proposal) partition reference material (`Proposal summary`) and action forms (`Rate & submit review` / `Comments`) into horizontal Carbon section tabs, automatically returning to the form tab when validation errors occur. Never show the rule number in the interface.
- **Filter Eligibility & Bounded Filter Panel Rule (D-76)**: Table filters are strictly for repeating, low-variety taxonomy columns (`Status`, `Category`, `Type`, `Role`, `Level`, `Stage`, `Outcome`, `Faculty`, `Alert`, etc., capped at `≤ 8` chips — collapsing to a compact searchable dropdown if higher or for explicit borderline entity filters like `Course / Subject`), dates as presets + From/To ranges (never lists of dates), and numbers as Min/Max ranges (never chip lists). Identifying and free-text columns (`Reference`, `Code`, `ID`, `Programme`, `Proposal`, `Title`, `Name`, `Proposer`, `Lecturer`, `Participant`, `Email`, `Cohort`, `Reason`, etc.) are **search-only** — a filter section must never grow with the amount of data. Filter sections are ordered by usefulness (Status first), and if a table has no filterable columns, the Filter button is hidden automatically. Search matches case- and accent-insensitively across all visible text columns with a concise, non-truncated placeholder (and full searchable column list on hover). Check every new table against this rule; never show the rule number in the interface.
- **Prohibition of Redundant Text & Overused Brackets**: Never add redundant explanatory blocks (e.g., "Where is this / What happens next / Who is responsible") or redundant section markers when UI context is obvious. Never wrap badges, tags, or buttons in square brackets `[...]` (use `FTMK`, `MQF 6`, `UMC`, `SAMC`, `Sign In`). Use standard spelling `"enroll"` / `"enrollment"` (not "enrol"). Card outlines must use crisp black (`#090a0f`).
- **Knowledge Base & Queries**:
  - Read `graphify-out/GRAPH_REPORT.md` first for questions regarding documents (Guide, Glossary, Decision Log, SRS, SDD, PRD, UI/UX Spec, Audit).
  - Query using `graphify query "<question>"`.

## 3. Application Architecture & Testing (`app/`)
- **Stack**: Laravel 13.38 / PHP 8.3 / MySQL 8.4 LTS (with PostgreSQL 16 backup) modular monolith (93 tables, 26 migrations, 243 routes, 135 Blade views, 7 active roles). Plain Blade + CSS (no Livewire/Vite/Redis). Single-language `EN | BM` toggle backed by `app/lang/ms.json` (3,211 keys).
- **Modules**: `app/app/Modules/*`
- **Serve**: `cd app; php artisan serve --port=8110`
- **Database**: Docker Compose (`docker compose up -d mysql` on port 3306; user `mcms:mcms`).
- **Tests**:
  - Pest: `php vendor/bin/pest` (410 tests, 5,900+ assertions, 100% green; run only one Pest run at a time to avoid deadlock on `mcms_test`).
  - Playwright: `npx playwright test` (headed Edge).
